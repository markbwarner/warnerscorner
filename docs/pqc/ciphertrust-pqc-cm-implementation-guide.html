01Zero Trust in a PQC World

Begin a measured migration now. Identify the information that must remain confidential for years, map the public key cryptography protecting it, and establish a pilot that can demonstrate both successful operation and rejection of invalid inputs. Thales CipherTrust Manager supports this program through centralized key management, release dependent ML DSA application signing, and ML-KEM for internal platform and supported connector communications.

Post quantum cryptography uses algorithms designed to resist attacks by both classical computers and sufficiently capable quantum computers. It runs on conventional infrastructure. The immediate concern is harvest now decrypt later: an adversary records encrypted traffic or wrapped keys today and attempts recovery when future capabilities permit. Health records, intellectual property, identity information, and long lived business secrets can retain value well beyond the lifetime of the application that created them.

Signing has a related but different objective. Migrating signatures protects the future authenticity of software, messages, and retained records. A signature does not encrypt a payload or prevent an attacker from harvesting it. Confidentiality and authenticity therefore need separate migration plans, with dependencies coordinated across the same systems.

Zero Trust requires explicit verification, limited privilege, and decisions based on current policy and evidence. PQC strengthens the cryptographic foundations of those decisions. The signing service still needs workload identity, authorization, key policy, audit records, and enforcement at the point of use. A compromised workload with signing permission can request a mathematically valid signature on malicious content.

02What quantum computing changes

A cryptanalytically relevant quantum computer could use Shor’s algorithm against RSA, finite field Diffie Hellman, and elliptic curve cryptography. That affects key establishment, certificates, and signatures. Increasing an RSA key size is not a durable PQC migration strategy. These algorithms are not suddenly broken on today’s ordinary computers; the migration addresses a future capability and exposure that can accumulate now.

MechanismPurposeMigration meaning
ML KEM · FIPS 203Establish a shared secret through encapsulation and decapsulationA key establishment building block used within authenticated protocols. In CipherTrust Manager, current use is limited to internal communications and supported connectors; application API or SDK use and ML-KEM key wrapping are not supported.
ML DSA · FIPS 204Digital signatures based on module latticesMigrate signing and verification together, including key distribution and artifact formats.
SLH DSA · FIPS 205Stateless hash based signaturesA distinct signature family. Availability, signature size, and performance differ from ML DSA. Standardization does not imply CipherTrust support.
AES 256 with authenticated encryptionProtect bulk data with symmetric keysRetain sound symmetric cryptography while reviewing key establishment, key wrapping, nonce handling, and access controls.
Hashes and MACsDigests and keyed integrity checksSelect strength for the use case. A bare digest is not proof of authorship. A MAC is shared key authentication, not public verification.

Grover’s algorithm provides a theoretical quadratic search advantage; it does not make AES obsolete in the same way that Shor’s algorithm threatens RSA and ECC. AES 256 offers a substantial margin, but no cipher is “bulletproof.” Protect keys, use approved implementations, and enforce correct modes and nonce management. Hash strength also depends on whether the application needs collision resistance or preimage resistance; avoid a universal rule that every hash must simply be doubled.

The first three NIST PQC standards were published in August 2024. Track current standards and errata rather than treating a product slide as a permanent standardization record. Algorithm standardization, product feature availability, algorithm validation, and a module’s FIPS 140 validation are separate facts.

03When to act and what to prioritize

There is no dependable date when a quantum computer will break deployed public key cryptography. Use a risk based planning horizon: the period for which data must remain secret, plus the time needed to migrate, may exceed the time remaining before an adversary gains the relevant capability. The uncertainty is a reason to prioritize long lived exposure now, rather than to promise a particular “Q day.”

  • Confidentiality first where exposure lasts: map captured traffic, key exchange, exported or wrapped data encryption keys, backups, and externally shared encrypted records. A strong AES cipher does not help if an attacker later recovers its key through a vulnerable public key mechanism.
  • Signatures where trust lasts: examine firmware roots, update systems, signing certificates, build artifacts, identity infrastructure, and retained legal records. Account for devices and consumers that cannot easily be upgraded.
  • Ecosystem dependencies: inventory vendors, protocols, clients, libraries, and validation requirements. Test interoperability and downgrade behavior before an enforced transition.

Use the current NIST transition guidance to inform the roadmap, then apply the deadlines that actually govern your organization. A federal migration target is not a forecast of a quantum breakthrough or an automatic deadline for every private enterprise.

05Signing and hashing in a Zero Trust design

Encryption protects confidentiality. Authenticated encryption such as AES GCM also detects changes for parties that possess the appropriate shared key. A digital signature adds verification using a public key and can preserve evidence of a specific signing key across storage, distribution, or multiple service hops. A plain hash detects changes only when the expected digest is obtained through a trusted channel; an attacker who can replace both the file and its hash defeats that check.

ControlProves or protectsStill required
AES GCMConfidentiality and integrity within a shared key security relationshipUnique nonces, correct tag verification, key protection, replay policy
Hash digestA reproducible fingerprint of exact bytesAn authenticated reference digest or signed manifest
ML DSA signatureIntegrity and association with a signing private keyTrusted public key binding, authorization, freshness, artifact policy
TLSProtection between the negotiated channel endpointsPayload signatures when evidence must survive termination or forwarding

A signature does not automatically establish a person’s identity, legal enforceability, safe software, or permission to deploy. Bind the public key to an approved identity and purpose; preserve key version, mode, context, and verification policy. Long term evidence may need trusted timestamps, certificate status evidence, archival renewal, and documented custody.

Context provides domain separation. For ML DSA it is an optional sequence of at most 255 bytes, supplied consistently by signer and verifier. It can distinguish FirmwareV1 from API-Payload-v1. It is not a secret or an anti replay mechanism. An API also needs a signed request ID, intended audience, timestamp or validity window, and a replay cache.

Use ML DSA where quantum resistant signatures meet the application’s needs and its verifiers support them. Assess larger public keys and signatures, runtime support, and validation requirements. Relative performance and size compared with other signature families depend on parameter sets and implementations; benchmark the actual path.

06Four practical signing use cases

1 Firmware and software updates

Sign an immutable release manifest containing the firmware digest, device family, version, and rollback policy. Use a dedicated production signing key and an application context such as FirmwareV1.

The device verifies the signature against a provisioned trust anchor, validates the manifest, and refuses incompatible images and rollback attempts. A signature alone does not enforce version policy.

2 Service to service API messages

Sign the exact serialized request envelope, including amount, currency, source, destination, request ID, audience, and expiry. Use API-Payload-v1 as a separate domain.

The receiving service checks the signature, signer authorization, intended audience, expiry, and replay state before acting. Reformatting JSON may change signed bytes.

3 Long term contracts and records

Use a documented detached signature format or a signing container that supports the chosen algorithm. Archive the content, signature, key identity, policy, and time evidence.

An auditor verifies the original bytes and evidence against an authenticated historical public key. A detached ML DSA blob is not automatically an interoperable PDF signature.

4 CI CD artifacts and SBOMs

Sign a release manifest or SBOM linked to an immutable artifact digest, build identity, source revision, and release version. Use a production key separated from development.

A deployment verifier enforces signature and signer policy and checks the artifact digest. Confirm the admission controller and signature format support ML DSA; an ordinary Kyverno or Gatekeeper installation does not create this integration automatically.

08Pure signatures pre hashing and external mu

A large firmware image need not force every architecture to buffer or transfer the entire image to a remote signer. The right approach depends on the supported signing interface and on where message processing is trusted. Pre hashing is primarily a data handling and bandwidth choice, not an automatic security improvement.

ModeInput and framingTradeoff
Pure ML DSAThe message and context are framed by ML DSASimpler semantic contract. A streaming implementation can avoid buffering, but a remote API may still transfer the full message.
HashML DSAA standardized pre hash construction binds a hash identifier, digest, and contextUseful for specialized workflows. Hash choice and encoding become part of the verification contract.
Pure ML DSA over a manifest or digestAn application defines and signs the manifest or digest as an ordinary messageValid if the format and hash are explicit, but this is not automatically HashML DSA.

HashML DSA is not HashEdDSA, and neither name means SLH DSA. An API flag that names a hash does not by itself establish standardized HashML DSA behavior. Likewise, a file path supplied as a string is not file contents unless the tool explicitly implements file input. Record the accepted hash functions, parameter set, mode, context encoding, and body encoding from the actual API.

With external mu, the application can hold only the public key while CipherTrust Manager retains the private key. That separation reduces key exposure, but the signing service may no longer inspect the original content. Authorization and release policy must therefore be enforced before a representative is accepted. “Hybrid” here describes split processing; it is not a classical plus PQC hybrid cryptographic construction.

09Build a CBOM that leads to migration work

A Software Bill of Materials identifies software components and dependencies. A Cryptographic Bill of Materials inventories cryptographic assets and their relationships: algorithms, parameter sets, protocols, certificates, libraries, and key metadata. Neither should contain private keys or secret material. Connect findings to system owners, sensitive data flows, exposure, and replacement work.

Scan source code, dependencies, configuration, deployment definitions, and supporting shell, PowerShell, Python, Java, and batch scripts. These surrounding files often select the algorithm or invoke a tool even when the main application hides the choice behind a library. Combine static findings with runtime negotiation evidence and vendor inventories. An algorithm string in a test fixture or README is not proof of production exposure.

10Three next steps

  • 1 Inventory and rank exposure. Choose a small number of high value systems. Build a CBOM and data flow map, identify long lived secrets and durable trust anchors, and assign an accountable owner to each migration dependency. Deliver a ranked backlog with evidence and explicit gaps.
  • 2 Prove a supported CipherTrust path. Verify the deployed release and operating profile, provision a dedicated pilot key, and test one ML DSA signing workflow with both endpoints under your control. Review ML-KEM protection separately for supported internal and connector communications. Include tampered data, wrong context, untrusted keys, denied callers, and fallback failures. Deliver repeatable results and latency measurements.
  • 3 Expand through governed releases. Agree on vendor and verifier readiness, key rotation and retirement, monitoring, recovery, and deployment gates. Track exceptions with expiry dates. Deliver a funded roadmap and an evidence package that distinguishes implemented controls from planned work.

Success is measurable coverage and enforced policy across a complete trust path. A PQC enabled key manager is a useful foundation; quantum readiness comes from the applications, protocols, identities, and operational controls that use it.

12Define exactly what is signed

Choose a versioned envelope and preserve its exact bytes. Signing a JSON object requires either a specified canonicalization scheme or an agreement to transport the original serialization without reformatting. A different property order, whitespace, newline, Unicode normalization, or number format can change the message. Base64 is a transport encoding, not hashing and not encryption.

A detached signature envelope should retain the signature bytes and encoding, immutable key ID and version, parameter set, signature mode, context bytes and encoding, manifest schema, and hash algorithm when applicable. The verifier must obtain its trusted keys and allowed algorithms from policy. It must not trust an arbitrary public key or mode chosen only by the envelope.

For API requests, add request ID, issuer, audience, issued at and expiry values. Sign these fields along with the business data. Verify before processing, then atomically record the request ID to prevent replay. A context string separates purposes but does not make an old transaction fresh.

For contracts, keep the original document bytes unchanged. If a PDF container is required, confirm the selected PDF signature profile and each consuming tool support the algorithm. Plan trusted timestamps, historical certificate evidence, revocation policy, and archival renewal independently of the raw signing operation. A signer’s identity and legal effect depend on that surrounding evidence.

HashML DSA end to end

  • Agree on a supported parameter set, approved hash or XOF, digest output length, context, and signature profile. Match collision resistance to the required signing strength; SHA 256 should not be claimed to preserve every ML DSA parameter set’s full strength.
  • Provision a dedicated key for the intended mode and purpose. FIPS 204 permits the same key pair for pure and pre hash modes but recommends separation; mode names do not create different lattice key mathematics.
  • Process the exact source content through the agreed hash. Confirm whether the API expects the full content or an already computed digest. Sending full content for server side hashing does not reduce network transfer.
  • Apply the standardized framing once through a supported implementation. Sign and store the signature with mode, hash identifier, context, and immutable key reference. Do not implement HashML DSA by passing a SHA hex string into ordinary pure signing and renaming the result.
  • The verifier processes the original content and enforces the same mode and hash profile. Test changed content, wrong hash, changed context, wrong key, malformed signatures, and disallowed mode fallback.

HashEdDSA describes pre hash variants in the EdDSA family; Ed25519 is quantum vulnerable. SLH DSA is a separate stateless hash based signature family. Neither is an alias for HashML DSA. Library and hardware support differ, so these names must remain explicit in policy and metadata.

Implement it only after confirming a supported CipherTrust external mu operation, its transport encoding, response format, and approved operating profile. If unavailable, use the supported pure message or signed manifest path instead.

A direct subprocess.run(["ksctl", ...]) integration requires a documented and tested CLI contract. Do not assume .signature rather than .data, do not pass context twice, and do not silently accept an empty signature. Keep credentials out of command line arguments where the platform exposes process listings; use the approved credential mechanism.

Public key only processing does not itself expose a private key. Generating a local software key for a laboratory test is also not automatically a compromise; it changes where the secret exists and how it must be protected. Production signing can keep private keys inside an approved boundary while using open source clients for public operations. A public key contains no secret, but its identity and version must remain trustworthy.

20Signing and encryption across multiple tiers

An application that already encrypts JSON may still need a signature. Determine which principals share encryption keys and where TLS or payload encryption terminates. AES GCM authenticates within the shared key relationship; every party holding that key can generate a valid tag. A signature can retain a distinct origin key association across intermediaries and allow verification without giving every consumer the signing secret.

If end to end evidence is required, sign a defined payload envelope and protect confidentiality using an authenticated encryption protocol. Sign then encrypt is one possible composition when the signed content and signature should be hidden, but it is not a universal rule for every protocol. Use an established message format or a reviewed construction that binds identities, recipients, algorithm choices, and application purpose. Validate the authenticated decryption result before parsing or acting on decrypted content.

Encryption, signatures, and freshness solve different problems. Do not describe ML DSA verification as “decrypting a signature” or as proving the content is true. It verifies a signature relation for a message and public key. Non repudiation claims also require identity evidence, key custody, policy, and applicable legal analysis.

Original content with approved key and contextExplicit positive verification and matching immutable artifact digest
One changed content byteVerification rejected; deployment blocked
Wrong context or empty contextRejected when the original signature used a different context
Wrong key or unauthorized key versionRejected by cryptography or trust policy
Malformed truncated or empty signatureRejected without crash or permissive fallback
Changed mode hash identifier or encodingRejected; never silently reinterpreted
Unauthorized signer or inactive keySigning denied and audit event retained
Replayed API request or expired envelopeRejected even if its signature is valid
Signer outage token expiry or TLS validation failureClear error; no unsigned release or verification bypass
Transport fallback to disallowed groupDetected and rejected according to migration policy
Key rotation and historical verificationNew releases use new key; retained releases verify under approved historical policy
Recovery and evidence retentionRestore exercise and retained audit evidence meet documented objectives

Capture the deployed release, CLI or SDK version, module and profile, algorithm and key version, request identifier, policy decision, latency, and positive or negative result. Restrict logs to necessary metadata; never log authentication tokens or private key material. Size logging retention to the use case and verify it independently of platform defaults.

For performance, measure full request latency, throughput at realistic concurrency, failure rates, payload and signature sizes, CPU cost at clients, and recovery after interruption. Compare pure message, signed manifest, and external mu paths where supported. Reduced network input does not automatically increase signing operations per second.

23Cryptographic design considerations

Common misconceptionDesign guidance
ML DSA repeatedly labeled FIPS 205ML DSA is FIPS 204; SLH DSA is FIPS 205.
AES described as bulletproof and fixed quantum datesUse qualified security statements and risk horizons; no dependable breakthrough date.
Hashing equated with sender authenticationA bare hash requires a trusted reference; signatures and MACs have different trust models.
Context claimed to prevent replayContext separates purposes. Freshness and replay rejection need signed application fields and state.
HashEdDSA equated to HashML DSADifferent algorithm families and constructions.
File path passed as body and assumed to upload fileRead bytes explicitly or use the tool’s documented file input facility.
Hex digest treated as standardized pre hash modeSigning digest text in pure mode is an application scheme, not automatically HashML DSA.
Same key prohibited across modesFIPS permits it but recommends mode separation; policy may impose stronger restrictions.
External mu supplied with context againContext is already bound in mu; follow the external operation’s documented parameter rules.
Public key described as safe to place anywhereIt is not secret, but integrity and identity binding are essential.
Open source use equated with private key exposureKey location and controls matter; public only client operations require no private key.
HTTP or CLI success treated as verification successRequire the documented explicit positive verification result.
HSM described as ML KEM only and fixed FIPS levelCapabilities and validation depend on model, firmware, client, and configuration.
Admission controller acceptance assumedImplement and test an ML DSA aware verifier and policy integration.
ML DSA described as encrypting or decrypting a hashUse algorithm specific sign and verify operations; no signature decryption model.
