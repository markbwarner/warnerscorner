Luna-only implementation model

Two Luna-native ways to protect the AES key.

This guide explains the Luna-native paths in this project. The first uses a standard, independently created AES key and wraps it with Luna RSA-OAEP. The second uses native Luna ML-KEM, which produces a secret key plus an encapsulation value as one operation. Both approaches use AES-256-GCM for content protection.

Mental model

Content encryption stays the same. Key establishment changes.

Luna RSA-OAEP

Create AES first, then wrap it

The application has a standard AES key before RSA begins. Luna performs the public-key wrap and private-key unwrap operations.

Luna ML-KEM

Encapsulate and obtain key material

Luna ML-KEM encapsulation returns a secret-key result plus encapsulation bytes. The receiver uses the private key plus encapsulation to obtain the matching result.

RSA-OAEP
1. Create AES keyA standard 32-byte AES key exists independently of the RSA keypair.
2. Luna wraps itThe Luna public RSA key encrypts the AES key with RSA-OAEP.
3. Luna unwraps itThe Luna private RSA key recovers the AES key for decryption.
ML-KEM
1. Luna encapsulatesThe Luna ML-KEM public key is used to run encapsulation.
2. Receive two outputsA secret-key result is available to the sender and encapsulation bytes are available for transport.
3. Luna decapsulatesThe Luna private ML-KEM key plus encapsulation yields the matching secret-key result.
Key distinction: RSA protects a key that already exists. Native ML-KEM establishes matching key material during encapsulation and decapsulation. In both cases, only the protected key artifact belongs in the envelope; raw secret key bytes are never a transport field.
Luna-native RSA

Standard AES key plus Luna RSA-OAEP wrapping.

The current Luna comparison creates a standard AES key for the RSA scenario and then calls Luna-provider RSA-OAEP for both wrap and unwrap. The AES key is not generated by ML-KEM in this path.

Current comparison sequence
KeyPair rsaKeyPair = session.generateEphemeralRsaKeyPair(3072);
SecretKey aesKey = generateDemoAesKey(32);

String wrappedAesKey = wrapAesKeyWithLunaPublicKey(
        aesKey, rsaKeyPair.getPublic());

SecretKey recoveredAesKey = unwrapAesKeyWithLunaPrivateKey(
        wrappedAesKey, rsaKeyPair.getPrivate());
AES creation

generateDemoAesKey(32) creates 32 random bytes and builds a standard SecretKeySpec. It is intentionally separate from RSA.

For production, decide whether AES keys should instead be generated and retained by Luna as persistent symmetric keys.

Luna RSA operations

The native RSA methods obtain RSA/ECB/OAEPWithSHA-256AndMGF1Padding from LunaProvider, then call WRAP_MODE with the Luna public key or UNWRAP_MODE with the Luna private key.

Native provider wrap and unwrap logic
Cipher cipher = Cipher.getInstance(
        "RSA/ECB/OAEPWithSHA-256AndMGF1Padding",
        LunaIntegrationSupport.LUNA_PROVIDER_NAME
);

cipher.init(Cipher.WRAP_MODE, lunaPublicKey, new SecureRandom());
String wrapped = Base64.getEncoder().encodeToString(cipher.wrap(aesKey));

cipher.init(Cipher.UNWRAP_MODE, lunaPrivateKey);
SecretKey recovered = (SecretKey) cipher.unwrap(
        Base64.getDecoder().decode(wrapped), "AES", Cipher.SECRET_KEY
);

The public key is not secret, but this native flow deliberately routes the wrap operation through Luna. The private-key unwrap is the critical HSM operation: the private RSA key remains Luna-backed while the HSM performs the unwrap.

Luna ML-KEM sender path

Encapsulation returns both a key result and a transport value.

LunaIntegrationSupport.LunaSession.encapsulateAesKey(...) maps the JDK KEM API result into the project record MlKemEncapsulationResult.

Project-level method signature
public MlKemEncapsulationResult encapsulateAesKey(
        PublicKey publicKey,
        int keyLengthBytes
) throws GeneralSecurityException

Internally, the method obtains the Luna ML-KEM implementation, creates an encapsulator using the recipient public key, requests an AES result of the required length, and returns both pieces.

KeyPair mlKemKeyPair = session.generateEphemeralMlKemKeyPair("ML-KEM-768");
MlKemEncapsulationResult result = session.encapsulateAesKey(
        mlKemKeyPair.getPublic(), 32);

SecretKey senderSecretKey = result.secretKey();
byte[] encapsulation = result.encapsulation();
result.secretKey()

In this project's Luna-native flow, this is a LunaProvider SecretKey that references the derived AES-256 key object in the HSM. It is not the 32-byte AES value in JVM memory. Pass this key object to a LunaProvider AES cipher; the provider sends its HSM key handle to Luna, which performs the AES operation while retaining the actual key material.

result.encapsulation()

The binary ML-KEM encapsulation. Base64-encode this for an envelope field such as wrappedAesKey; this is the transport value for the receiver.

What is sent: Base64 of result.encapsulation(). What is not sent: the SecretKey object, a Luna key handle, or raw AES key bytes. The receiver decapsulates the transport value with its Luna-resident private key and receives its own usable SecretKey object.
What encapsulation does, step by step
// Inside LunaSession.encapsulateAesKey(publicKey, 32)
KEM kem = KEM.getInstance("ML-KEM", "LunaProvider");
KEM.Encapsulator sender = kem.newEncapsulator(recipientMlKemPublicKey);
KEM.Encapsulated encapsulated = sender.encapsulate(0, 32, "AES");

SecretKey senderSecretKey = encapsulated.key();
byte[] transportBytes = encapsulated.encapsulation();

newEncapsulator(...) selects the recipient public ML-KEM key. encapsulate(0, 32, "AES") asks Luna to establish an AES key result of 32 bytes, or 256 bits. Luna returns two related outputs: a Luna-backed key object for the sender to use immediately with AES-GCM and 1,088 ML-KEM-768 transport bytes for the receiver. The project uses reflection around this JDK API so the source can still compile in environments where the KEM class is not available at compile time.

Build the sender's outbound envelope
MlKemEncapsulationResult result = session.encapsulateAesKey(
        recipientMlKemPublicKey, 32);

Map<String, ProtectedField> sensitive = encryptFieldsWithLuna(
        payload.sensitive(), result.secretKey());

ProtectedDocument outbound = new ProtectedDocument(
        UUID.randomUUID().toString(),
        "mlkem-key-1",
        0,
        new AlgorithmMetadata("ML-KEM-768", "AES-256-GCM"),
        payload.status(),
        payload.nonSensitive(),
        sensitive,
        Base64.getEncoder().encodeToString(result.encapsulation()),
        Map.of()
);

This is the sender boundary: AES-GCM encrypts the sensitive JSON values using result.secretKey(); the serialized envelope carries the ciphertext, IVs, algorithm metadata, key identity, and Base64 encapsulation. It never carries the sender's AES key object.

Luna ML-KEM receiver path

Decapsulation combines the private key with the transported encapsulation.

Project-level method signature
public SecretKey decapsulateAesKey(
        PrivateKey privateKey,
        byte[] encapsulation,
        int keyLengthBytes
) throws GeneralSecurityException
SecretKey receiverSecretKey = session.decapsulateAesKey(
        mlKemKeyPair.getPrivate(), receivedEncapsulation, 32);
1. Decode

The receiving service Base64-decodes the envelope’s encapsulation field to restore the original binary bytes.

2. Decapsulate in Luna

The Luna-backed private ML-KEM key and encapsulation are passed to the native decapsulator.

3. Decrypt fields

The returned Luna SecretKey is supplied to LunaProvider AES-GCM to recover the original application values.

Complete Luna ML-KEM envelope round trip
// Sender: create the Luna AES key object and encrypt the sensitive fields.
MlKemEncapsulationResult senderResult = session.encapsulateAesKey(
        recipientMlKemPublicKey, 32);
Map<String, ProtectedField> protectedFields = encryptFieldsWithLuna(
        payload.sensitive(), senderResult.secretKey());

// Transport: send only the Base64 encapsulation, IVs, and ciphertexts.
String wrappedAesKey = Base64.getEncoder()
        .encodeToString(senderResult.encapsulation());

// Receiver: recreate its Luna AES key object from the private ML-KEM key.
byte[] receivedEncapsulation = Base64.getDecoder().decode(wrappedAesKey);
SecretKey receiverSecretKey = session.decapsulateAesKey(
        recipientMlKemPrivateKey, receivedEncapsulation, 32);

// Use the receiver's Luna key object to recover the original JSON fields.
Map<String, String> originalSensitiveFields = decryptFieldsWithLuna(
        protectedFields, receiverSecretKey);

String name = originalSensitiveFields.get("name");
String cardNumber = originalSensitiveFields.get("creditCardNumber");

The sender and receiver receive different Java key objects, each backed by Luna, but ML-KEM establishes matching AES key material. The ciphertext therefore decrypts to the original values when the receiver uses its decapsulated Luna key object.

Luna AES-GCM field helpers
private static ProtectedField encryptFieldWithLuna(
        String plaintext, SecretKey lunaAesKey, byte[] iv)
        throws GeneralSecurityException {
    Cipher cipher = Cipher.getInstance(
            "AES/GCM/NoPadding", LunaIntegrationSupport.LUNA_PROVIDER_NAME);
    cipher.init(Cipher.ENCRYPT_MODE, lunaAesKey,
            new GCMParameterSpec(128, iv));

    byte[] ciphertext = cipher.doFinal(
            plaintext.getBytes(StandardCharsets.UTF_8));
    return new ProtectedField(
            Base64.getEncoder().encodeToString(ciphertext),
            Base64.getEncoder().encodeToString(iv));
}

private static String decryptFieldWithLuna(
        ProtectedField protectedField, SecretKey lunaAesKey)
        throws GeneralSecurityException {
    Cipher cipher = Cipher.getInstance(
            "AES/GCM/NoPadding", LunaIntegrationSupport.LUNA_PROVIDER_NAME);
    cipher.init(Cipher.DECRYPT_MODE, lunaAesKey,
            new GCMParameterSpec(128, Base64.getDecoder()
                    .decode(protectedField.iv())));

    byte[] plaintext = cipher.doFinal(Base64.getDecoder()
            .decode(protectedField.ciphertext()));
    return new String(plaintext, StandardCharsets.UTF_8);
}

Call the first helper for every sensitive field with a fresh 12-byte IV. Store each ciphertext and IV in the JSON envelope. On the receiver, call the second helper with the same field values and the receiverSecretKey returned by decapsulation.

Envelope handling

The content envelope stays familiar in both Luna paths.

The envelope format is the same for either Luna RSA or Luna ML-KEM. It stores AES-GCM ciphertext and IV values for sensitive fields, then places either the RSA-wrapped AES key or the ML-KEM encapsulation into the transport field.

Luna deployment checklist

Questions to answer before using either path in a service.

  1. Is the recipient RSA or ML-KEM private key generated and retained as a Luna-backed key object or persistent token object?
  2. Does the service use LunaProvider for both RSA wrap and unwrap operations when the target architecture requires a fully Luna-native RSA flow?
  3. For ML-KEM, does the service use LunaProvider for both KEM and AES-GCM operations with the returned Luna SecretKey?
  4. Does the message format carry algorithm, key ID, key version, Base64 transport value, IV, and ciphertext consistently?
  5. Are ML-KEM parameter set and requested AES key length the same at the sending and receiving ends?
  6. Are diagnostics that print private keys, AES key bytes, or encapsulation values disabled outside the learning demo?
  7. Are performance results labeled as Luna-native RSA or Luna-native ML-KEM rather than compared to a different provider model?
