01Zero Trust in a PQC World

Begin a measured migration now. Identify the information that must remain confidential for years, map the public key cryptography protecting it, and establish a pilot that can demonstrate both successful operation and rejection of invalid inputs. Thales CipherTrust Manager supports this program through centralized key management, release dependent ML DSA application signing, and ML-KEM for internal platform and supported connector communications.

Post quantum cryptography uses algorithms designed to resist attacks by both classical computers and sufficiently capable quantum computers. It runs on conventional infrastructure. The immediate concern is harvest now decrypt later: an adversary records encrypted traffic or wrapped keys today and attempts recovery when future capabilities permit. Health records, intellectual property, identity information, and long lived business secrets can retain value well beyond the lifetime of the application that created them.

Signing has a related but different objective. Migrating signatures protects the future authenticity of software, messages, and retained records. A signature does not encrypt a payload or prevent an attacker from harvesting it. Confidentiality and authenticity therefore need separate migration plans, with dependencies coordinated across the same systems.

Zero Trust requires explicit verification, limited privilege, and decisions based on current policy and evidence. PQC strengthens the cryptographic foundations of those decisions. The signing service still needs workload identity, authorization, key policy, audit records, and enforcement at the point of use. A compromised workload with signing permission can request a mathematically valid signature on malicious content.

02What quantum computing changes

A cryptanalytically relevant quantum computer could use Shor’s algorithm against RSA, finite field Diffie Hellman, and elliptic curve cryptography. That affects key establishment, certificates, and signatures. Increasing an RSA key size is not a durable PQC migration strategy. These algorithms are not suddenly broken on today’s ordinary computers; the migration addresses a future capability and exposure that can accumulate now.

MechanismPurposeMigration meaning
ML KEM · FIPS 203Establish a shared secret through encapsulation and decapsulationA key establishment building block used within authenticated protocols. In CipherTrust Manager, current use is limited to internal communications and supported connectors; application API or SDK use and ML-KEM key wrapping are not supported.
ML DSA · FIPS 204Digital signatures based on module latticesMigrate signing and verification together, including key distribution and artifact formats.
SLH DSA · FIPS 205Stateless hash based signaturesFor general-purpose enterprise signing, ML-DSA is often a practical first choice because it offers significantly smaller signatures and generally faster signing than SLH-DSA. Not currently supported in CipherTrust Manager.

Grover’s algorithm provides a theoretical quadratic search advantage; it does not make AES obsolete in the same way that Shor’s algorithm threatens RSA and ECC. AES 256 offers a substantial margin, but no cipher is “bulletproof.” Protect keys, use approved implementations, and enforce correct modes and nonce management. Hash strength also depends on whether the application needs collision resistance or preimage resistance; avoid a universal rule that every hash must simply be doubled.

The first three NIST PQC standards were published in August 2024. Track current standards and errata rather than treating a product slide as a permanent standardization record. Algorithm standardization, product feature availability, algorithm validation, and a module’s FIPS 140 validation are separate facts.

03When to act and what to prioritize

There is no dependable date when a quantum computer will break deployed public key cryptography. Use a risk based planning horizon: the period for which data must remain secret, plus the time needed to migrate, may exceed the time remaining before an adversary gains the relevant capability. The uncertainty is a reason to prioritize long lived exposure now, rather than to promise a particular “Q day.”

  • Confidentiality first where exposure lasts: map captured traffic, key exchange, exported or wrapped data encryption keys, backups, and externally shared encrypted records. A strong AES cipher does not help if an attacker later recovers its key through a vulnerable public key mechanism.
  • Signatures where trust lasts: examine firmware roots, update systems, signing certificates, build artifacts, identity infrastructure, and retained legal records. Account for devices and consumers that cannot easily be upgraded.
  • Ecosystem dependencies: inventory vendors, protocols, clients, libraries, and validation requirements. Test interoperability and downgrade behavior before an enforced transition.

Use the current NIST transition guidance to inform the roadmap, then apply the deadlines that actually govern your organization. A federal migration target is not a forecast of a quantum breakthrough or an automatic deadline for every private enterprise.

05Signing and hashing in a Zero Trust design

Encryption protects confidentiality. Authenticated encryption such as AES GCM also detects changes for parties that possess the appropriate shared key. A digital signature adds verification using a public key and can preserve evidence of a specific signing key across storage, distribution, or multiple service hops. A plain hash detects changes only when the expected digest is obtained through a trusted channel; an attacker who can replace both the file and its hash defeats that check.

ControlProves or protectsStill required
AES GCMConfidentiality and integrity within a shared key security relationshipUnique nonces, correct tag verification, key protection, replay policy
Hash digestA reproducible fingerprint of exact bytesAn authenticated reference digest or signed manifest
ML DSA signatureIntegrity and association with a signing private keyTrusted public key binding, authorization, freshness, artifact policy
TLSProtection between the negotiated channel endpointsPayload signatures when evidence must survive termination or forwarding

A signature does not automatically establish a person’s identity, legal enforceability, safe software, or permission to deploy. Bind the public key to an approved identity and purpose; preserve key version, mode, context, and verification policy. Long term evidence may need trusted timestamps, certificate status evidence, archival renewal, and documented custody.

Context provides domain separation. For ML DSA it is an optional sequence of at most 255 bytes, supplied consistently by signer and verifier. It can distinguish FirmwareV1 from API-Payload-v1. It is not a secret or an anti replay mechanism. An API also needs a signed request ID, intended audience, timestamp or validity window, and a replay cache.

Use ML DSA where quantum resistant signatures meet the application’s needs and its verifiers support them. Assess larger public keys and signatures, runtime support, and validation requirements. Relative performance and size compared with other signature families depend on parameter sets and implementations; benchmark the actual path.

Hash API versus the signing hashAlgo parameter

The standalone hash API and the signing operation perform different jobs. Using the hash API does not enable a pre-hash signature mode on the sign endpoint.

OperationHash selectionResult
POST /v1/crypto/hashThe JSON algorithm field selects a digest such as SHA3-256. The data field contains Base64-encoded input bytes.A digest of the input. No signing key is used and no digital signature is created.
RSA signing through /v1/crypto/signWhere required by the supported RSA signature scheme, hashAlgo selects the message digest used as part of signing. The selected padding and other scheme parameters must also match.A digital signature using an RSA private key. The verifier must use the same signature scheme and digest.
ML-DSA signing through /v1/crypto/signOmit hashAlgo on the interface described here. ML-DSA applies its standardized internal hashing, including SHAKE256 message processing.An ML-DSA signature over the supplied message and context. The internal hash processing is part of the algorithm, not a caller-selected RSA-style digest setting.

ML-DSA does use hashing internally. The rejection of hashAlgo means that this endpoint does not accept a separately selected signing digest; it does not mean that ML-DSA performs no hashing. SHA3-256 in the hash API and SHAKE256 inside ML-DSA are different functions. HashML-DSA is a separate standardized pre-hash construction and is not enabled simply by adding hashAlgo.

Algorithm background: NIST FIPS 204 and NIST FIPS 202 SHA-3 and SHAKE functions.

06Four practical signing use cases

1 Firmware and software updates

Sign an immutable release manifest containing the firmware digest, device family, version, and rollback policy. Use a dedicated production signing key and an application context such as FirmwareV1.

The device verifies the signature against a provisioned trust anchor, validates the manifest, and refuses incompatible images and rollback attempts. A signature alone does not enforce version policy.

2 Service to service API messages

Sign the exact serialized request envelope, including amount, currency, source, destination, request ID, audience, and expiry. Use API-Payload-v1 as a separate domain.

The receiving service checks the signature, signer authorization, intended audience, expiry, and replay state before acting. Reformatting JSON may change signed bytes.

3 Long term contracts and records

Use a documented detached signature format or a signing container that supports the chosen algorithm. Archive the content, signature, key identity, policy, and time evidence.

An auditor verifies the original bytes and evidence against an authenticated historical public key. A detached ML DSA blob is not automatically an interoperable PDF signature.

4 CI CD artifacts and SBOMs

Sign a release manifest or SBOM linked to an immutable artifact digest, build identity, source revision, and release version. Use a production key separated from development.

A deployment verifier enforces signature and signer policy and checks the artifact digest. Confirm the admission controller and signature format support ML DSA; an ordinary Kyverno or Gatekeeper installation does not create this integration automatically.

08Build a CBOM that leads to migration work

A Software Bill of Materials identifies software components and dependencies. A Cryptographic Bill of Materials inventories cryptographic assets and their relationships: algorithms, parameter sets, protocols, certificates, libraries, and key metadata. Neither should contain private keys or secret material. Connect findings to system owners, sensitive data flows, exposure, and replacement work.

Scan source code, dependencies, configuration, deployment definitions, and supporting shell, PowerShell, Python, Java, and batch scripts. These surrounding files often select the algorithm or invoke a tool even when the main application hides the choice behind a library. Combine static findings with runtime negotiation evidence and vendor inventories. An algorithm string in a test fixture or README is not proof of production exposure.

ApproachUseful evidenceLimit to account for

Network observationObserved certificates, endpoints, and negotiated protocolsEncrypted or unobserved paths and inactive configurations remain blind spots.
Enterprise discoveryHosts, services, ownership, certificates, installed softwareApplication code semantics and migration effort may need further work.
Migration planning scannerCandidate work packages and likely ownershipHeuristic findings require validation and do not certify quantum readiness.

One example is the PII and PQC application migration scanner, a planning aid for connecting cryptographic clues to likely migration work. Evaluate it against representative repositories, including known vulnerable cases, false positives, and scripts. Measure finding accuracy and coverage rather than assuming it replaces enterprise discovery. 09Three next steps

  • 1 Inventory and rank exposure. Choose a small number of high value systems. Build a CBOM and data flow map, identify long lived secrets and durable trust anchors, and assign an accountable owner to each migration dependency. Deliver a ranked backlog with evidence and explicit gaps.
  • 2 Prove a supported CipherTrust path. Verify the deployed release and operating profile, provision a dedicated pilot key, and test one ML DSA signing workflow with both endpoints under your control. Review ML-KEM protection separately for supported internal and connector communications. Include tampered data, wrong context, untrusted keys, denied callers, and fallback failures. Deliver repeatable results and latency measurements.
  • 3 Expand through governed releases. Agree on vendor and verifier readiness, key rotation and retirement, monitoring, recovery, and deployment gates. Track exceptions with expiry dates. Deliver a funded roadmap and an evidence package that distinguishes implemented controls from planned work.

Success is measurable coverage and enforced policy across a complete trust path. A PQC enabled key manager is a useful foundation; quantum readiness comes from the applications, protocols, identities, and operational controls that use it.
