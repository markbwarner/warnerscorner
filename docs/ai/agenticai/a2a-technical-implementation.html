Protect A2A solution overview

Protecting agent-to-agent workflows with CipherTrust

A Python reference implementation that shows how to verify agent admission, protect sensitive values between business steps, and investigate the resulting security events.

A reference design pattern intended for agentic AI.

Why it matters

In a multi-agent application, each handoff can expose data to another service. A trip planner can work with a protected fax reference. The fax service needs the destination to make the handoff. In an insurance workflow, an approval step can use a protected customer identifier while a payment integration has a different need for the underlying banking data.

Protect A2A puts admission, routing, and data handling in shared services. The orchestrator determines the business sequence. Each agent card describes the agent’s identity, address, skills, and data policy. The gateway uses the verified card to determine how to deliver the request.

CipherTrust Manager provides trust records for registration. CipherTrust RESTful Data Protection (CRDP) performs the protect and reveal operations requested at runtime.

Implementation guide

Services, interfaces, and startup

The registry, gateway, and adapter run as separate Python processes. Orchestrators are command-line callers. Each task agent runs its own FastAPI application. Start with the registry, bring up the gateway, adapter, and required task agents, then run the corresponding orchestrator after confirming registration and discovery.

Control plane

How an identity becomes a verified agent

  1. Provision the authoritative record. CipherTrust Manager stores approved identities and the expected code fingerprint and mode for each. The User Set also carries invocation metadata. An administrative utility computes source hashes and updates the configured User Set. Review the approved inventory and file paths before using it against a shared environment.
  2. Submit the registration. The startup helper reads the identity certificate and hashes the relevant source file. The submitted keys are card, certificate, and code_hash. Orchestrators register as callers before running their workflows. Their task endpoints are unnecessary for those runs.
  3. Evaluate the claims. The registry verifies the certificate signature using the local CA certificate, compares its common name with the trusted record and the card name, and checks the reported fingerprint. It derives a mode from the card’s flags and compares it with the approved mode.
  4. Publish verified metadata. The registry stores the enriched card in memory and issues a random time-limited token associated with that identity. The gateway later uses discovery to obtain the target address and policy. Invocation metadata is published for integration use.

Runtime

The exact request and response path

Each orchestration step chooses a target and sends the task to /proxy. The incoming credential identifies the registered caller. The target name resolves the destination and provides a data policy. The JSON-RPC-style shape is specific to this demo, so integrations should agree on an explicit protocol and contract.

The registered caller supplies its registry token in X-Registry-Token. The gateway normalizes the declared names, matches the sender with the validated identity, requests discovery data, and applies a sliding-window limit per verified caller. The current configuration uses a one-hour registry token lifetime, a five-minute gateway verification-cache lifetime, and 200 accepted requests per 555-second window for the rate check. The registry, token cache, and request history are process-local.

Request outcomes to distinguish
StageGateway behaviorInterpretation
Caller credentialHTTP 401 for missing or invalid token or an unavailable validation pathNo task delivery was attempted by that request.
Caller bindingHTTP 403 if the claimed sender differs from the registered token identityThe request identity check failed.
Target resolutionHTTP 404 and discovery_failed for an unresolved targetCheck whether the intended target registered successfully and appears in discovery.
Traffic limitHTTP 429 and rate_limit_exceededThe caller reached the configured request limit. Review the workflow’s volume and retry behavior.
ForwardingRecords delivery_success or delivery_failedCheck the response body and downstream business result as well as the transport outcome.

For an admitted call the gateway attaches a request correlation ID and a run ID and forwards using its downstream gateway credential. The task response commonly places business output in result.output. Gateway outcomes and task outcomes should be validated independently. A scripted approval string, for example, describes the handler’s response.

Runtime data policy

Protect, reveal, and standard forwarding

Mode selection and coverage
Mode on the verified cardTransformationScope
requires_tokenizationProtect recognized sensitive text before forwarding.String-valued parameters. The demo matches formats such as phone numbers, email addresses, and numeric identifiers.
requires_revealRequest reveal under the target identity and substitute returned values.Marked references in params.input. The configured CRDP profiles and identity privileges govern the result.
Public modeForward after identity, discovery, and rate checks.No protect or reveal transformation is selected. The request still goes through the gateway.

The protection adapter receives the mode, input value, target identity, originator, and correlation context. It validates and classifies the input, chooses a numeric or character profile, and sends a CRDP request. Successful protect results are marked for later recognition. Reveal returns the CRDP value when available. The demo does not recursively inspect arbitrary nested payloads or apply general response redaction.

A recognized protect failure produces a gateway error and stops delivery. Reveal needs separate result validation. This checkout can forward an unresolved value after a reveal attempt, and the recorded reveal count tracks matched references rather than guaranteed plaintext results. Require an explicit acceptable reveal result before integrating any high-impact downstream task.

Travel from itinerary request to fax

The travel orchestrator sends the trip request with a contact value in its input and a separate user_fax parameter. The planner’s verified card selects protect mode. The gateway scans matching strings and passes the result to the planner, which assembles a fixed itinerary and includes the fax parameter in its reply.

Implementation example

Insurance stages and current handoff limits

The insurance caller starts with a sample policy, claim, customer identifier, and estimate. The workflow is orchestrated in Python with five task calls. The agent results illustrate distinct data roles. The demo stores no claim in a database and connects to no payment rail.

Insurance input, decision, and integration boundary
StageWhat crosses the gatewayObserved implementation contract
Claim validationCustomer identifier to a protect-mode target.The gateway protects a recognized identifier. The handler returns the received identifier for subsequent use.
ApprovalProtected customer identifier and estimate to a public-mode target.The handler returns APPROVED as a fixed value. Introduce a real policy decision before wiring approval to an actual disbursement.
Bank lookupSample account and routing inputs to a protect-mode target.The handler reads digits from the already processed request, then formats account and routing values with token markers. It simulates lookup rather than querying a bank database.
PaymentTwo values extracted by the caller from the bank result.The payment card selects reveal. The current caller strips the markers, so this checkout does not establish automatic CRDP reveal on that handoff. The payment handler echoes its input in a simulated result.
NotificationCustomer reference to a reveal-mode target.The handler returns the received value after removing a leading marker if present. Validate the reveal policy and implement actual last-four masking and delivery before using a customer-facing channel.

The card skill identifiers and the orchestrator’s labels differ for some insurance stages. The current handlers are routed by endpoint and read the input directly. An integration should align identifiers, validate dispatch, and decide which fields are safe in results and console output.

The default insurance entry point also invokes an additional bank-lookup stress scenario after the business demo. Interpret its log activity separately when comparing workflow outcomes. Historical logs describe the sample run and may reflect a different request path from this checkout.
