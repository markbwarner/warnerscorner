The registry checks which agents can join, the gateway decides how each request should reach its destination, CipherTrust processes values that need protection or reveal, and the offline dashboard shows the recorded outcomes.

High-level flow

From agent startup to a report

  1. Define the trust record

    An administrator sets the approved identities, source fingerprints, and data modes in a CipherTrust Manager User Set. The registry has a local copy of the issuing CA certificate.

  2. Register the agent or caller

    The service submits a card, its certificate, and its reported file hash. The registry checks the request, indexes the verified card, and issues an expiring token. Routine business requests happen after registration.

  3. Choose the next task

    The orchestrator names a destination and sends a task input to the gateway. For travel, its calls are plan, fax, and weather. It starts the fax call using the planner’s returned itinerary.

  4. Check identity, target, and volume

    The gateway verifies the caller’s registry token, checks the claimed sender, resolves the destination from verified cards, and applies the per-caller rate limit.

  5. Apply the destination’s data policy

    The gateway selects protect, reveal, or forwarding without transformation. It calls the Thales adapter for the values that need CRDP processing.

  6. Deliver the request and return the result

    The agent gets the processed input via the gateway, runs its task handler, and returns its result. The orchestrator can use that result for another call.

  7. Record and review the outcome

    Structured records show onboarding, gateway outcomes, and data-protection activity. The dashboard reads historical logs and filters the records in the browser.

The first two steps happen at onboarding. The request steps repeat for every agent call. The reporting step reads saved logs separately.

Runtime decisions

What does the gateway do next?

Decision points you can observe
ConditionActionWhat to check
Caller verified and target uses protectRecognize sensitive values in string parameters, call CRDP for each recognized value, and forward the processed request.Check the value received by the destination and the corresponding protect activity.
Caller verified and target uses revealLook for marked references in the input, request reveal for the receiving identity, and use the returned value where available.Check the actual reveal result and downstream input. A reveal event with zero affected references can be recorded.
Caller verified and target uses public modeDeliver the task without choosing a protect or reveal operation.Expect a delivery result. Public describes the transform mode and the caller still goes through the gateway.
Target missing or request rate exceededReturn a target-discovery or throttling error before calling the agent.Look for discovery_failed or rate_limit_exceeded.
Protection service cannot protect a recognized valueStop the protect request when the gateway receives a protection failure.Check both the adapter and gateway records, then confirm the destination did not run.

Reveal and protect have different failure handling in this checkout. An unresolved reveal can reach the task handler, so a high-impact integration needs an explicit fail-closed rule for required values.

Policy flow and sample outcomes

Where the system makes each decision

What a blocked registration looks like

Identity missing from the trusted set

The certificate names an agent with no entry in the CipherTrust Manager User Set. The registry refuses the registration.

Unauthorized Agent: Your identity is not in the trusted registry.

Agent card and certificate names differ

The registry refuses registration when the agent card name differs from the certificate’s common name.

Identity Mismatch: Card name does not match Certificate CN.

Registry token

An expiring credential associated with a verified caller. The gateway uses it when deciding whether to admit a request.

Protected reference

A marked representation of a protected field. A subsequent step can carry it to a reveal-capable target under the applicable CRDP policy.

Explanation to reuse. The caller chooses what happens next. The registry establishes which identities and policy modes are admitted. The gateway decides how to deliver each request. CipherTrust protects or reveals eligible values, and the dashboard shows the recorded evidence.
