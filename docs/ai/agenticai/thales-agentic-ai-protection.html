Consistent data protection across agent teams

As agents take on more business tasks, they pass customer records, account details, and other sensitive values between services. A shared protection layer gives security teams a consistent place to govern those handoffs and lets developers focus on the task each agent performs.

  • Limit sensitive data exposure

    Pass protected references through planning and approval steps. Reveal only the fields a permitted destination needs to complete its work.

  • Apply policy centrally

    Manage keys and protection policies in CipherTrust Manager. Use a gateway to apply those policies consistently across participating workflows.

  • Give reviewers usable evidence

    Capture agent admission, data protection, and delivery activity so teams can explain what happened at each handoff.

Agent2Agent protocol

What is A2A?

A2A is an open, vendor-neutral protocol for AI agents to discover what other agents can do, exchange messages, and collaborate on tasks across network and enterprise boundaries. Google introduced it in April 2025 and contributed it to the Linux Foundation in June 2025.

Think of A2A as a shared language for AI agents. Frameworks like LangGraph or CrewAI govern how an agent makes decisions and runs its workflow. A2A standardizes the messages independent agents exchange across that boundary. Standard bindings include JSON-RPC 2.0 over HTTP, HTTP with JSON, and gRPC. HTTP bindings can use Server-Sent Events (SSE) to stream updates.

A2A protocol base architecture

  1. Discover. An A2A client or orchestrator obtains an Agent Card from a well-known URL, direct configuration, or an optional registry or catalog.
  2. Send a message. The client selects a skill and sends a request to the remote A2A agent at its advertised endpoint.
  3. Track work and receive results. A server can reply with a message or return a task for ongoing work. Tasks can report progress, request more input, complete, or fail. Artifacts carry outputs such as documents or structured results.

Agent Cards are digital business cards

An Agent Card is a JSON document clients read during discovery and setup. It describes the agent’s identity, service endpoint, capabilities, authentication requirements, and skills. The client uses it to choose an agent, format the request, and establish how to connect securely.

Open agent ecosystem

A common A2A boundary for the tools you choose

Any agent development platform or orchestrator can participate through a compatible A2A endpoint or adapter. The Thales protection layer gives these independently built agents a common place to apply security policy.

CipherTrust Manager
Provides centralized key management and protection policies. In this pattern, it also supplies the trusted records the registry uses to check agent admission.
A2A registry
Checks an agent’s registration against approved identity and policy records, then makes the verified agent card available for discovery.
Security gateway and CRDP
The gateway checks the caller, resolves the destination, and applies its data policy. CipherTrust RESTful Data Protection (CRDP) performs the requested protect or reveal operation.

Where the pattern fits

Google Agent Development Kit
Expose a specialist agent through A2A and publish an Agent Card for discovery.
LangGraph
Keep state and routing in the graph. Delegate cross-agent work through an A2A integration and apply a separate protection policy to any persisted state that needs it.
CrewAI or a custom orchestrator
Keep the existing team roles and workflow logic. Connect participating agents to the gateway through compatible A2A endpoints or adapters.
Model Context Protocol (MCP)
Use MCP alongside A2A when an agent needs access to tools or data. An MCP tool can provide a separate integration path to CRDP.

Production design pattern

Why the gateway belongs in the request path

The orchestrator sends the task to the security gateway. The registry verifies the agent at enrollment, while the gateway evaluates the actual request before it reaches the destination. This gives teams a second decision point even after a caller has been admitted.

Sanitize data before delivery
Suppose a travel request to the Weather Agent includes a Social Security number. In a deployment with a rule for that field and destination, the gateway can protect the value with CRDP or reject the request. Teams implement the rule at the shared handoff instead of adding tokenization to every agent.
Enforce policy after registration
Keep task endpoints reachable through the gateway, verify caller credentials at runtime, and enforce permitted destinations and reveal privileges. Even an admitted agent remains subject to those checks. Per-caller rate limits help contain runaway loops and repeated requests.
Make audit evidence easier to collect
Route protect and reveal through a common path. Correlate gateway events with CipherTrust protection records to see who requested reveal, which destination needed it, and when. For example, an event can show that the gateway requested reveal for the fax service at 14:00. That evidence supports audit reviews for requirements such as PCI DSS and HIPAA. CRDP audit logging
Separate agent development from cryptography
Business developers work with protected references where the task permits it. Security teams manage keys and policies centrally. Supported changes, such as moving an eligible field to format-preserving encryption, can often be localized to the policy or adapter. New algorithms, including post-quantum options, depend on platform support and integration requirements.

Data protection in practice

Each agent receives the data its task requires

Consider a travel workflow that plans a trip and then sends an itinerary by fax. The planner can carry a protected fax reference in the itinerary. The fax service needs the actual destination at the point of delivery.

Protect before planning
The orchestrator submits the task and destination. The gateway uses CRDP to protect the selected value before forwarding it to the planner.
Carry the reference forward
The planner returns an itinerary containing the protected reference. The orchestrator passes that itinerary to the next step.
Reveal at the point of use
The gateway requests reveal under the fax service’s identity. The configured protection and access policies determine the result.

Customer evaluation

Show how the policy worked across the workflow

Follow the evidence from an agent’s registration through request processing and downstream delivery. The sample dashboard shows how security and operations teams can review activity across travel and insurance scenarios.

What teams can evaluate

  • Admission. See which identities the registry admits and why it refuses registrations with mismatched trust records.
  • Data handling. Compare the value each step receives and verify any reveal against the intended destination policy.
  • Operational controls. Review discovery, rate-limit, protection, and delivery outcomes to support investigations and audit evidence collection.
  • Cryptographic agility. Manage supported changes through the protection layer, reducing the number of agent applications that need changes.

A focused pilot

Choose one workflow with a sensitive handoff. Bring the orchestration tooling you already use, identify which agent needs each data view, and evaluate the protected and revealed results alongside the recorded events.
