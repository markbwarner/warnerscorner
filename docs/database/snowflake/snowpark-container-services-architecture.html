How the Snowflake deployment works

A service function routes SQL arguments to the Java controller.

Snowflake SQL and the service-function binding run outside SPCS. Snowflake batches values and sends them to the private udfendpoint of thales_udf_service. Spring Boot listens on 8083; routes such as /protectbulkchar and /revealbulkchar select processing. The adapter calls CRDP’s /v1/protectbulk or /v1/revealbulk over the backend’s internal DNS on 8090, then maps results back to SQL. This SQL path does not require the GCP API Gateway or external-function API integration used by the Cloud Run option.

Snowflake context and service configuration have different jobs.

CONTEXT_HEADERS = (CURRENT_USER) provides the SQL user context. The controller trims and lowercases the name for CRDP’s reveal username. Snowflake roles and function/service permissions control invocation; CRDP evaluates the reveal policy. The current SPCS code also has a DEFAULTREVEALUSER fallback, unlike the Cloud Run handler’s required-context validation. Include user context explicitly. Connection/TLS settings come from the service configuration; this is not the Cloud Run handler’s arbitrary static-header contract.

Size the adapter and the cryptographic backend independently.

A compute pool supplies capacity and Snowflake places service instances within it. Set service instance counts and per-container resource requirements for each workload. The two services can share suitable pool capacity or use separate pools; the diagram does not imply one container pair per instance or fixed placement on a node. Measure both services when tuning batches, concurrency, and capacity. Scaling Java does not automatically create a matching CRDP instance. Service behavior ↗

Use CRDP_HOST for the backend’s internal DNS name and CRDP_PORT for its API port. The two services do not communicate through localhost. Configure permitted outbound connectivity to Manager; the diagram does not imply an automatic external network grant.

Three UDF-to-CRDP transport modes

CRDP modeTransportClient identity
no-tlsHTTPNo client certificate.
tls-cert-optHTTPSServer certificate validation; no client certificate required by this setup.

The SPCS deployment guide uses a private TCP endpoint for CRDP TLS so CRDP terminates the connection. Configure CA trust, matching certificate DNS SANs, and mounted TLS secrets. These modes describe this project’s adapter-to-CRDP path.

A native SQL service function

CREATE OR REPLACE FUNCTION
  THALES_CRDP_SCS_REVEALBULK_CHAR(input VARCHAR)
RETURNS VARCHAR
RETURNS NULL ON NULL INPUT
SERVICE = thales_udf_service
ENDPOINT = udfendpoint
CONTEXT_HEADERS = (CURRENT_USER)
MAX_BATCH_ROWS = 5000
AS '/revealbulkchar';

Example from the SPCS deployment guide. Select your database/schema and provision the service first. Keep APP_INPUT_FORMAT=external for the compatible JSON row envelope; that setting does not make this a CREATE EXTERNAL FUNCTION. Use your actual policy defaults and measured batch limits.

What belongs in each layer?

  • Snowflake: SQL, service-function bindings, image repository, compute pools, private service endpoints, roles, and secrets.
  • Java adapter: data-type routes, policy selection, input/output mapping, batching, and reveal user context.
  • CRDP: protect/reveal operations and configured access-policy evaluation.
  • CipherTrust Manager: centralized key/policy management and CRDP registration.

The reference image is conceptual. This project’s CRDP path calls REST bulk APIs; it does not require an additional CADP-library hop or a KMIP link between Java and CRDP.

Choose the deployment around your operating model

SPCS is a fit for Snowflake-centric teams who want service functions and platform-native operations. Cloud Run fits teams who operate a shared protection API in GCP and want integration with their cloud IAM, networking, observability, and release processes. Both expose supported container configuration; neither provides direct administration of an underlying Kubernetes cluster.
