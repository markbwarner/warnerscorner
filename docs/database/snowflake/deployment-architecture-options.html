THALESDEPLOYMENT ARCHITECTURE OPTIONS

The same objective, with different deployment contracts. Both examples connect SQL to Thales CRDP. Cloud Run uses an external function and GCP gateway; SPCS uses a native service function. Port settings, endpoint paths, identity handling, and transport options belong to each implementation and should not be copied unchanged between them.

Option 01 / Google Cloud

Cloud Run with a CRDP sidecar

Snowflake → API Gateway
Java :8181 ⇄ localhost ⇄ CRDP :8090

Java and CRDP share each Cloud Run instance. Google manages runtime infrastructure, while your team operates the GCP project configuration. Scaling adds another container pair.

  • GCP IAM, VPC integration, Secret Manager, and Cloud Logging.
  • Independent cloud API lifecycle and access for authorized clients.
  • Cross-platform authentication, networking, and data transfer to plan.

Choosing a deployment model

Cloud Run sidecar or Snowpark Container Services?

Both can host a Java adapter and CRDP containers. In this design, Snowflake uses an external function through API Gateway; an SPCS design can use a Snowflake service function. The application workflow can be similar, but deployment, authentication, and operations differ.

More control over the cloud environment—not direct Kubernetes administration. Cloud Run lets an organization operate this service in its own GCP project and apply its cloud identity, network, release, and observability practices. SPCS exposes its own container and compute-pool controls. Neither provides customer access to the underlying Kubernetes control plane, node administration, custom schedulers, or arbitrary cluster settings. Use GKE if those cluster-level controls are required.

Cloud Run is attractive when…

  • Your platform team already operates IAM, networks, monitoring, and CI/CD in GCP.
  • You want an independently deployed protection API usable beyond Snowflake.
  • Organizational policy prefers application runtime ownership in your cloud project.

SPCS is attractive when…

  • Snowflake is the main consumer and your team prefers native service functions and role-based operations.
  • Keeping data processing in the Snowflake-managed environment is a priority.
  • You want fewer cross-platform authentication and deployment components in the SQL request path.

Tradeoffs to validate: Cloud Run introduces cross-platform IAM and networking, plus transfer and cold-start considerations. SPCS couples this deployment to Snowflake’s available regions, instance families, and service model. Both require CRDP registration planning and correct access policies. Neither is inherently faster, cheaper, or more secure; compare representative batch workloads, data-handling requirements, and the full operating cost. These selection points are architectural assessments, not measured results.
