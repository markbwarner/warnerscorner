What happens behind the endpoint?

The SQL function calls a persistent Java HTTP service.

Snowflake sends rows, settings, and user context through API Gateway. The gateway authenticates to Cloud Run using its backend service account. The Java invoker keeps a JVM and HTTP server running for the instance lifetime, loads function.jar, and maps each request to the handler. Java calls the CRDP API over localhost:8090; the response travels back through Java and the gateway. A new JVM is not launched for every SQL row.

You define the service; Google manages its execution.

A revision captures your container images and runtime configuration. Cloud Run starts instances with both Java and CRDP, shares their local network, and manages their lifecycle. Your team controls the exposed service settings and deployment process within GCP. Sidecars and declarative YAML provide familiar Kubernetes-style concepts, with a service-level operating model. Multi-container deployment ↗

Scaling adds another Java + CRDP pair.

The startup dependency waits for CRDP’s /healthz on 8080 before Java starts on 8181. When Cloud Run adds instances, each gets its own CRDP sidecar; CRDP is not one shared backend for all instances. The documented starting configuration uses a minimum of one instance, a maximum of two, concurrency one, and instance-based billing for background CPU. These are example settings, not a live inventory. Idle capacity incurs charges; replacements can re-register CRDP clients, so token reuse and ephemeral state must be planned.

Three ports. Three distinct responsibilities.

ListenerPortPurpose
Java ingress8181Cloud Run routes authenticated service traffic to Java.
CRDP API8090Java calls protectbulk / revealbulk over localhost.
CRDP health8080Cloud Run checks /healthz for this CRDP version.

Java uses 8181 because CRDP’s health listener already occupies 8080. Only Java is the configured ingress container; CRDP has no separate public service endpoint in this design.

Control where your platform team works

Runtime configuration: set CPU and memory per container, concurrency, instance limits, startup checks, and container dependencies within Cloud Run’s supported limits.

GCP operations: use your project’s IAM, Secret Manager, Cloud Logging, image registry, deployment pipelines, and supported VPC networking options.

Independent releases: update the protection service through the cloud team’s processes while preserving the Snowflake SQL interface.

SPCS also supports resource settings, probes, service scaling, and compute-pool configuration. The key choice is the operating environment and integration model, not simply “more container settings.”

Application settings and identity

HEADERS = (
  'CRDPIP' = 'localhost',
  'CRDPPORT' = '8090',
  'mode' = 'revealbulk',
  'protection-profile' = 'char-external',
  'keymetadata' = 'YOUR_EXTERNAL_VERSION'
)
CONTEXT_HEADERS = (CURRENT_USER)

Illustrative SQL fragment, not a full function definition. Java reads settings from sf-custom-* headers with environment fallbacks, and normalizes the reveal user to lowercase. CRDP evaluates its access policy. A direct Cloud Run test also requires an IAM identity token and invocation permission; a user-context header is not an authentication token.

Choosing a deployment model

Cloud Run sidecar or Snowpark Container Services?

Both can host a Java adapter and CRDP containers. In this design, Snowflake uses an external function through API Gateway; an SPCS design can use a Snowflake service function. The application workflow can be similar, but deployment, authentication, and operations differ.

More control over the cloud environment—not direct Kubernetes administration. Cloud Run lets an organization operate this service in its own GCP project and apply its cloud identity, network, release, and observability practices. SPCS exposes its own container and compute-pool controls. Neither provides customer access to the underlying Kubernetes control plane, node administration, custom schedulers, or arbitrary cluster settings. Use GKE if those cluster-level controls are required.

Cloud Run is attractive when…

  • Your platform team already operates IAM, networks, monitoring, and CI/CD in GCP.
  • You want an independently deployed protection API usable beyond Snowflake.
  • Organizational policy prefers application runtime ownership in your cloud project.

SPCS is attractive when…

  • Snowflake is the main consumer and your team prefers native service functions and role-based operations.
  • Keeping data processing in the Snowflake-managed environment is a priority.
  • You want fewer cross-platform authentication and deployment components in the SQL request path.

Tradeoffs to validate: Cloud Run introduces cross-platform IAM and networking, plus transfer and cold-start considerations. SPCS couples this deployment to Snowflake’s available regions, instance families, and service model. Both require CRDP registration planning and correct access policies. Neither is inherently faster, cheaper, or more secure; compare representative batch workloads, data-handling requirements, and the full operating cost. These selection points are architectural assessments, not measured results.
