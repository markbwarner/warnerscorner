Thales JDBC for Databricks

Bring policy-based protect and reveal controls to Databricks without forcing teams to redesign how they query data

Managed cloud data platforms make analytics easier to operate, but they also limit backend customization. The Thales Databricks JDBC solution closes that gap by moving policy-aware protect and reveal behavior to the client side so applications, BI tools, and JDBC-based workflows can continue using familiar SQL.

Why customers care

Organizations want the operational simplicity of Databricks and other managed cloud data services, but still need practical ways to protect, reveal, and govern sensitive fields such as PII, payment data, healthcare data, and regulated identifiers.

  • Managed platforms simplify infrastructure, scaling, and operations.
  • Thales Batch Data Transformation can already protect sensitive fields before or during data loading.
  • The hard part is dynamic reveal for analytics, reporting, JDBC tools, and shared data access workflows.
  • Teams need a solution that works with normal SQL instead of requiring every tool or application to embed custom security code.
Positioning summary

This is a business-focused solution for customers who want to preserve the usability of Databricks while extending Thales policy controls into JDBC-based access paths.

  • Keep standard BI and JDBC workflows intact.
  • Apply policy and user-based outcomes outside the managed database service.
  • Return ciphertext, masked values, or cleartext based on policy.
  • Reduce dependency on one-off custom application integrations.
Problem
  • Managed cloud databases simplify operations but limit backend customization.
  • Examples include Amazon RDS, Google Cloud SQL, Azure managed databases, and Databricks SQL environments.
  • Customers can protect data, but dynamic reveal remains difficult.
Current limitation
  • Managed services typically do not allow customer-controlled backend reveal logic such as UDF-based approaches.
  • Customers are often pushed toward custom application code to handle reveal decisions.
  • That approach does not scale well across BI, reporting, admin, and analyst workflows.
Why that matters
  • Custom code is harder to scale, test, and maintain.
  • It does not work well with JDBC-based tools and shared analytics platforms.
  • This creates a gap in delivering a complete protect-and-reveal solution for modern cloud data estates.

Thales - Databricks JDBC Business Overview 1
Business Value

What the Thales JDBC solution changes for Databricks customers

The value is not just technical integration. The value is that customers can extend Thales data protection into JDBC-based analytics and application access without waiting for custom backend database functions or rewriting every consumer of the data.

Thales JDBC driver solution

  • Moves protect and reveal transformation to the client side.
  • Allows applications and JDBC tools to continue using normal SQL.
  • Applies policy- and user-based handling outside the managed database service.
  • Brings governed access to Databricks query workflows without forcing teams into custom code for every use case.

Business outcome

  • Enables ciphertext, masked, or cleartext results based on policy.
  • Extends protection and reveal to JDBC-based applications and tools.
  • Provides a more complete solution for managed cloud database environments.
  • Supports collaboration between security, analytics, and engineering teams without changing how each group works day to day.

Typical customer journey

1
Protect the data once

Use Thales Batch Data Transformation, ETL workflows, or existing data onboarding processes to protect sensitive fields before they are broadly consumed.

2
Define policy and user outcomes

Security teams decide who should see ciphertext, masked values, or cleartext and manage those decisions centrally in Thales policy tooling.

3
Let applications and BI tools use JDBC normally

Analysts, developers, and reporting tools continue to query Databricks through standard JDBC patterns.

4
Apply Thales outcomes at read time

The wrapper evaluates the configured field mappings, user context, and policy path and returns the right form of the data for the requesting user.

Key benefits and capabilities

Leverages Thales CRDP bulk processing

Uses existing Thales CRDP bulk capabilities to support higher-volume protect and reveal flows where the policy path allows it.

Easy overrides for new protected columns

New field mappings can be introduced through configuration and runtime properties for many use cases, reducing the need to rebuild or redeploy the driver jar.

Kill switch available

Operational teams can disable wrapper behavior quickly when troubleshooting, validating, or isolating issues in shared environments.

Detailed logging for supportability

Verbose logging helps customers and support teams understand policy path selection, field handling, and reveal decisions during rollout and troubleshooting.

Sample utilities included

Sample data-load and transformation utilities help teams validate policies, load test data, and debug field mappings faster during implementation.

Supports JDBC-based ecosystems

Extends Thales protection into BI clients, admin tools, SQL editors, application services, and reporting workflows that depend on JDBC access.

Executive message: the Databricks JDBC solution helps customers move from raw protection building blocks to a more complete protect-and-reveal operating model for managed cloud data platforms.

Architecture Snapshot

Simple view of how the Databricks JDBC solution works

This architecture view is intentionally high level. The important point is that Databricks continues to run the SQL workload, while the Thales wrapper adds policy-aware transformation around JDBC access.

Process summary

1
Application or BI tool connects over JDBC

The client connects through the Thales-enabled Databricks JDBC entry point while the standard Databricks JDBC driver remains the underlying delegate driver.

2
SQL continues to run normally

Existing query patterns remain familiar for analysts, applications, and reporting platforms using supported JDBC workflows.

3
Protected fields are resolved from policy-driven config

Configured object mappings determine which returned fields require Thales evaluation and which policy path applies.

4
Thales applies the correct outcome at read time

Based on policy and user context, the solution returns ciphertext, masked values, or cleartext without requiring backend database UDF customization.

Client layer
Applications, BI tools, JDBC workloads

DbVisualizer, analytics clients, reporting tools, notebooks, and custom JDBC applications.

Thales layer
Thales Databricks JDBC wrapper

Resolves protected columns, applies runtime controls, and orchestrates policy-aware transform behavior.

Vendor layer
Standard Databricks JDBC driver

The Databricks driver still handles the database connectivity path and remains part of the runtime design.

Data platform
Databricks SQL and governed data

Queries continue to run against Databricks while Thales extends policy-aware data handling around JDBC access.

Policy services
CRDP or CADP Centralized

Thales services drive the final data handling outcome according to policy, user access, and configured operating mode.

For security teams

Centralizes data handling decisions without forcing every consuming team to build its own reveal logic.

For analytics teams

Keeps Databricks and JDBC access patterns familiar so teams can focus on insights instead of bespoke security integration work.

For engineering teams

Provides a reusable client-side pattern for managed cloud data environments where backend customization is limited or unavailable.
