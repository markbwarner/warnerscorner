Why this matters

JDBC drivers are the software layer that lets Java and JDBC-based tools communicate with databases. By enhancing that layer, organizations can apply protection and reveal logic close to the data-access path instead of rewriting every analytics application or dashboard.

The result is a practical pattern for cloud modernization: sensitive data stays protected at rest, yet authorized users can still work through familiar tools such as DbVisualizer, BI platforms, report builders, ETL utilities, and custom JDBC applications.

How the drivers work

The driver sits between the JDBC client and the target cloud database. SQL flows normally to the database. As result sets are read back, the Thales-aware driver inspects configured protected columns and invokes the correct Thales service only when needed.

Step 1

Application or BI tool connects over JDBC

The client uses a Thales-enabled JDBC driver instead of a standard vendor driver.

Step 2

SQL is sent normally to the target database

No application rewrite is required for ordinary query execution, inserts, or dashboard access.

Step 3

Protected fields are identified in the result set

Configured fields such as `email|tag.char` or `creditcard|tag.nbr` drive the reveal behavior.

Step 4

Thales services enforce policy at read time

CRDP and CADP Centralized determine whether the user receives ciphertext, masked data, or revealed values.

Two operating models

  • Thales CRDP uses REST-based protect and reveal APIs, including bulk operations for high-volume paths.
  • Thales CADP Centralized supports centralized protection controls and policy enforcement with Thales key management.

Performance-aware controls

  • Batch mode can group result-set values into chunked CRDP bulk calls.
  • Allowlist logic can skip reveal requests entirely for users outside a licensed or authorized userset.
  • Chunking, debug controls, and profile-based field mapping help tailor performance to each tool.

Business value for cloud analytics and operations

The solution is designed for organizations that want to move analytics, reporting, and operational access to the cloud without giving up policy-based control of sensitive data. It combines database portability with centralized protection.

Where it fits well

  • Developer and DBA access through JDBC tools.
  • BI and reporting workloads that need controlled visibility into sensitive fields.
  • Cloud migration projects moving from on-premises databases to managed services.
  • Shared data environments where different users may require ciphertext, masked data, or plaintext outcomes.

Why Thales matters here

  • CipherTrust Manager acts as the keeper of keys, protection policies, and access decision logic.
  • CRDP and CADP Centralized provide a consistent protection model that travels with the data-access workflow.
  • Security policy remains externalized from the application and database schema design.

Benefits

  • Protect sensitive cloud database fields without changing how analysts query data.
  • Use the same driver strategy across AWS RDS, GCP Cloud SQL, and Azure database services.
  • Keep Thales at the center of key custody and policy governance.
  • Scale higher-volume read paths with CRDP bulk APIs while keeping a consistent user experience.
  • Platforms such as Snowflake and Databricks with platform-specific drivers are also available.
