How the Thales Databricks JDBC solution works

The Thales Databricks implementation adds a policy-aware wrapper around the standard Databricks JDBC driver. Applications and BI tools continue to issue normal SQL, while the wrapper identifies configured protected fields and applies Thales policy before result values are returned to the client.

Core pattern

This is a wrapper-plus-delegate-driver design. The Databricks JDBC driver still handles the actual connection to Databricks SQL Warehouses. The Thales layer sits in front of it and adds config resolution, protected-field detection, runtime identity evaluation, and policy enforcement.

  • Standard Databricks driver remains required. The Thales driver delegates to the vendor driver rather than replacing it.
  • Ordinary SQL still works. Existing query logic, dashboard access, and JDBC workflows continue using standard statements.
  • Protection is config-driven. Object mappings and tag aliases determine which fields participate in reveal behavior.
  • Read-time outcomes are policy-driven. Returned values may be ciphertext, masked data, or cleartext depending on user and policy.
Typical clients

DbVisualizer, BI tools, custom Java applications, JDBC-based services, validation jobs.

Key config

protect.object.my_catalog.my_schema.table, TAG.*, MODE, BATCHMODE, BATCHSIZE.

Identity model

For token-based Databricks connections, the wrapper can use captured SQL session identity instead of the literal JDBC username.

Policy engines

CRDP for REST-based protect/reveal flows, or CADP Centralized for centrally managed protection policy behavior.

Architecture Flow

Runtime sequence

The wrapper inspects result metadata and configured field mappings, then routes only protected values through Thales enforcement services.

1

Connect through the wrapper

The application uses the Thales Databricks JDBC entry point. The wrapper loads configuration, prepares runtime properties, and opens the actual connection through the Databricks JDBC driver.

2

Execute SQL normally

Standard Databricks SQL continues to run against the SQL Warehouse. The wrapper does not require broad query rewrites for normal read access.

3

Resolve protected columns

The wrapper matches returned columns against object-scoped mappings such as protect.object.my_catalog.my_schema.customer_table and the related TAG.* aliases.

4

Apply Thales policy

Only protected fields are sent through CRDP or CADP Centralized, which decide whether the caller should receive ciphertext, masked data, or cleartext.

Implementation Notes

Configuration and operational guidance

Config model

Use object-scoped mappings wherever possible. A typical pattern is protect.object.my_catalog.my_schema.customer_table=email|tag.char.internal with separate TAG.* alias definitions for policy name and policy type.

Runtime overrides

Connection-level overrides are useful for testing, but wrapper-only properties should stay internal to the Thales layer and should not be passed through to the Databricks JDBC driver as database configuration.

Identity behavior

For token-based connections, the JDBC username may be the literal value token. The wrapper can instead capture the Databricks SQL session identity and use that for allowlist and reveal decisions.

Utility jobs

Backend protect, unprotect, and reprotect utilities should use a raw Databricks connection for table scan and update paths so values are not auto-revealed before explicit service operations run.

Summary

The Databricks solution is best described as a policy-aware JDBC wrapper around the standard Databricks JDBC driver. Applications keep ordinary SQL behavior, while the Thales layer applies protected-field detection, user-aware reveal logic, and service-based enforcement when results are read.
