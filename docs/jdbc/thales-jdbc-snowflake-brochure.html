Thales JDBC for Snowflake

Bring policy-aware protection and reveal controls to Snowflake JDBC workflows

The Thales Snowflake JDBC wrapper lets applications, SQL tools, and BI clients keep using familiar Snowflake SQL while configured protected fields are evaluated through Thales at read time.

Why customers care

Snowflake enables high-value analytics and collaboration. Teams also need a practical way to keep policy decisions around sensitive values consistent across developer tools, analyst workflows, reporting, and custom JDBC applications.

  • Keep JDBC-based workflows familiar for analysts and developers.
  • Apply Thales policy to configured PII and sensitive fields at read time.
  • Support CRDP REST or CADP Centralized policy paths.
  • Use the connected database identity for user-aware policy outcomes.
Typical clients

DbVisualizer, JDBC applications, ETL validation jobs, reporting tools, SQL editors, and services that use the Snowflake JDBC driver.

What stays the same

Snowflake continues to own connectivity, authentication, session state, SQL execution, metadata, and warehouse processing.

What Thales adds

Protected-field detection, user normalization, policy-aware reveal calls, batching, and optional CipherTrust userset checks.

Data protection model

Use internal policies, external policies with stored metadata headers, or a static metadata fallback when appropriate.

Thales Snowflake JDBC Business Overview1
Business Value

Extend data-centric controls into common Snowflake access paths

The value is not a replacement for Snowflake security. The value is a reusable client-side pattern for applying Thales data-protection policy to fields returned through JDBC.

Protect once, govern consistently

Protect sensitive values before broad consumption, then use the JDBC layer to invoke reveal policy for configured result-set fields.

Preserve familiar tools

Teams continue with normal Snowflake JDBC connections and SQL rather than embedding a custom Thales integration in every consumer.

Add or adjust data sources without rebuilding

GUI tool and JDBC connection properties can override Thales settings for a datasource, helping teams test policies and introduce new connections without recompiling the wrapper.

Configure protection at the right scope

Define common protected fields globally with app.fieldstoprotect, then use protect.object.<table> for table- or view-specific mappings.

Fail closed with allowlist control

Allowlist mode restricts reveal to explicitly authorized CipherTrust userset members. A missing or failed lookup skips reveal, making it a practical emergency containment control.

Use enterprise-friendly authentication

CipherTrust Manager authentication supports password and client-credential modes, with credentials sourced from configuration, environment variables, or Akeyless.

Executive message: the Snowflake JDBC wrapper lets organizations extend Thales policy-based data handling into everyday SQL and JDBC workflows without replacing Snowflake or forcing every consuming team to write its own reveal integration.
Thales Snowflake JDBC Business Overview2
Architecture Snapshot

Snowflake executes SQL; the wrapper controls protected values on return

The wrapper delegates to the standard Snowflake JDBC driver. It intercepts JDBC results, matches configured protected fields, and invokes Thales only for those returned values.

1

Connect through the wrapper

The application uses com.thales.snowflake.wrapper.ThalesSnowflakeDriver, which delegates connection handling to the Snowflake JDBC driver.

2

Run Snowflake SQL normally

Snowflake manages the session, role, warehouse, database, schema, query execution, and underlying result set.

3

Resolve protected fields

Object-scoped mappings such as protect.object.EMPLOYEES_EXTERNAL determine which returned columns are sent to Thales.

4

Apply Thales reveal policy

The wrapper supplies the normalized database user and, for external fields, per-row metadata headers when the result includes them.
