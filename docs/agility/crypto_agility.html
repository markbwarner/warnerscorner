What is crypto agility?

One weekend, I watched my son dunk a basketball in our neighborhood and wished I could move as quickly and easily as he did. It got me thinking about a phrase I kept hearing at work: crypto agility. What does it take for a system to change direction with the same control?

Crypto agility is the ability to replace or adapt cryptography while preserving security and keeping systems running. It applies to keys, algorithms, parameters, certificates, and protocols. A routine key rotation is one example. Retiring a weak algorithm or replacing a compromised certificate authority tests the same capability under more pressure. NIST guidance

Speed
Make approved changes promptly through tested procedures.
Balance
Keep services and authorized access working through the cutover.
Strength
Use suitable cryptography and contain exposure when a key or algorithm fails.
Coordination
Align policy, applications, data migration, and operations.

Three pillars of crypto agility

A key management service provides a place to enforce key policy and record lifecycle events. The surrounding applications, libraries, and operating procedures determine how quickly and safely changes can reach production.

01

Key generation

Generate keys with a cryptographic random bit generator backed by a trustworthy entropy source. Entropy measures unpredictability. A long key derived from a predictable seed can still be easy to guess.

Set the target security strength for the data and its protection lifetime. Then choose an appropriate algorithm, key size or parameter set, and generation process. Use a validated cryptographic module where required and enforce key export rules. NIST entropy guidance

02

Algorithm support

Maintain a library of supported, NIST-approved algorithms and parameter sets for each purpose, such as encryption, key establishment, and digital signatures. Record where each option is supported, its approved uses, and when it must be retired.

For post-quantum readiness, test ML-KEM for key establishment and ML-DSA or SLH-DSA for signatures where relevant. Check interoperability, key and message sizes, performance, and support across libraries, protocols, and vendors. NIST PQC standards

03

Key lifecycle management

Track key states from pre-activation and active use through deactivation, archival where required, and destruction. Define a separate response for suspected compromise, including stopping affected use, assessing exposure, and replacing the key.

Record the key ID, version, owner, purpose, algorithm, permitted operations, and labels such as environment and data classification. Track creation, activation, rotation, and retirement dates. Schedule rotation, test permitted backup and recovery, and log approvals and changes.

Separate key and policy administration, application access, change approval, and audit review. NIST key management guidance

How to build and test crypto agility

A vulnerability, a change in standards, or an expiring certificate can force a cutover on someone else's timetable. Post-quantum migration adds a reason to start early, especially for systems that protect data with a long confidentiality lifetime. DES and RC4 show how widely deployed choices can become obsolete. An inventory and a rehearsed cutover let teams act before a change becomes urgent. NIST guidance

  1. Inventory cryptographic dependencies. Map keys, certificates, algorithms, protocols, libraries, and vendors to workloads, owners, and the data they protect. Prioritize by data lifetime, exposure, and service criticality.
  2. Set policy and assign owners. Define approved algorithms, key lifetimes, access rules, and emergency authority. Use public key infrastructure (PKI) to track certificate issuance and renewal. Document supplier dependencies and how to replace a certificate authority if necessary.
  3. Design for change. Put supported choices behind stable interfaces and version policies and protected data where the design allows. Preserve the metadata needed to read retained records and restore backups.
  4. Rehearse and measure. Pilot a rotation or algorithm swap. Test old reads, new writes, access controls, and recovery. Measure time to cut over and confirm where the old version is still used. Define when to pause or recover safely.
  5. Retire and verify. Confirm migration and retention requirements before disabling and ultimately destroying obsolete keys. Review audit evidence and update the incident response runbook and inventory.

Cryptography embedded in application code

When the application selects the algorithm or references a specific key directly, a change can require developers to update code or configuration and operations to deploy it. Data owners may also need to plan re-encryption and verify that downstream jobs can read migrated records.

Policy-driven field protection

When the application calls CRDP using a protection policy, security administrators can make supported policy or key changes centrally. If the API and data format stay compatible, a change can avoid an application code update. Operations and data owners still validate the rollout and migrate existing data where required.

Use field-level protection at a trusted ingestion point or for selected database columns. Before changing a policy, verify which settings your deployed versions support, test consumers that depend on the protected format, and decide how to handle existing data. Protection and audit controls can support a compliance program.

Summary

My son could change direction on the court because he'd practiced the move. The same applies to a cryptographic change. Speed comes from knowing where cryptography is used and having approved replacements ready. Balance comes from preserving access during the cutover. Strong keys and suitable algorithms protect the data, while clearly assigned roles keep the rollout coordinated.

A good first drill is to rotate one production-like workload's key, verify that old records remain readable and new writes use the new version, then prove that the old key can be retired safely. The drill shows where a larger algorithm change or post-quantum migration would require more preparation.
