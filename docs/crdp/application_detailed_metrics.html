What application metrics should help you decide

Application metrics show how a workload behaves over time: how often it calls CRDP, how long users wait, and how often requests or individual items fail. The goal is to know when behavior changes, which applications are affected, and who should investigate. A rise in failed requests can come from a bad release, a saturated pod, an expired credential, or attempted misuse. One chart rarely tells you which.

  • Find and troubleshoot application bugs: compare error categories, retries and batch item failures by caller and release. Use a request ID to find a representative failure in logs or traces.
  • Detect infrastructure issues and measure performance: compare request rate, timeout rate and p95 latency with pod CPU, restarts and readiness. Measure from the caller as well as the backend to catch failures before CRDP receives the request.
  • Investigate possible abuse: look for unusual reveal activity, repeated denials or new source networks. Use verified identities and audit events to investigate; unusual activity alone is not proof of compromise.
  • Scale in Kubernetes: choose signals that show pressure additional replicas can relieve, such as sustained CPU saturation or a growing queue. Test that scaling actually improves latency and throughput.

Expect to combine multiple capabilities for comprehensive coverage: application or gateway telemetry for the caller, CRDP counters for backend activity, pod telemetry for infrastructure, and audit events for accountability. Balance that coverage against implementation and maintenance costs. Start with existing collectors, a small set of consistent fields, and dashboards with named owners. Developers need evidence to reproduce failures; DevOps needs capacity and dependency signals; security administrators need evidence of misuse; DBAs need to understand batch impact; auditors need attributable records and retention controls.

Measure the application that makes the call

Use an authenticated caller identity at the request boundary for per-application metrics. Use CRDP and Kubernetes telemetry to explain what happened downstream.

A calling application is the business workload that initiates a request, such as HRAPP1 or HRAPP2. In a multi-tier design, it calls an enterprise security middleware service, which is the immediate API caller to CRDP. A CipherTrust Manager (CM) CRDP application is a separate configuration and registration boundary for CRDP clients. In this design, it often represents a business unit or policy boundary such as HR. A CRDP client_id identifies a registered CRDP runtime client, not the middleware's workload credential, the original business application, or a human user.

Two callers can share the same HR CRDP deployment without losing attribution. Give them separate credentials, validate those credentials at the existing gateway or security service, and map the verified principal to a stable caller_app. Keep the workload identity and the end user's authorization context separate. Never accept a caller-supplied application header as proof of identity.

Dashboards use rates and latency distributions to spot changes. Logs and traces provide request context for investigating them. In a zero trust design, authenticate each hop and enforce reveal authorization for the applicable workload and user.

Use a shared security service for common protection workflows

When several applications need the same protection workflows, use a company-owned wrapper to call a versioned security API. The wrapper handles the client contract and correlation; the shared service validates input, authorizes protect or reveal, maps approved policy aliases, calls CRDP and interprets the result. Developers integrate a business-facing API without having to implement cryptography or CRDP-specific logic in each application.

This is a useful target when refactoring direct integrations: security teams can standardize redaction and audit fields, and platform teams can test and evolve the CRDP integration once. Load-balance redundant middleware replicas and use contract tests, staged deployments and dependency tests to roll out changes. Plan for the extra network hop and shared failure domain: set timeouts, limit retries, and monitor middleware and CRDP capacity separately.

Expose the security API through an approved gateway or private ingress. An edge control such as Imperva API Security can complement the gateway and service's own authorization. Where a DMZ is part of the network design, terminate external access at the controlled ingress and restrict traffic into the private middleware tier. Keep CRDP on a private network reachable only from authorized middleware and approved operational paths. Authenticate both hops and prevent bypass routes.

One shared endpoint can report separately on HRAPP1 and HRAPP2 by grouping on verified workload identity. Use app-specific endpoints only when contracts or access boundaries differ, and authorize callers for those routes. A route or a self-reported app name is not proof of identity. Include optional workflow, client version, and correlation metadata for troubleshooting, while deriving caller identity, operation and authorization results at the trusted service.

What the service adds: if HRAPP1 receives HTTP 200 but 3 of 100 items fail, the gateway sees one successful HTTP exchange, the middleware records one partial failure and three failed items for HRAPP1, and CRDP counters show work across the shared runtime. That caller-to-item link is what makes the middleware valuable for reporting.

Recommended starting point: reuse an existing authenticated gateway and instrument the calling application or shared SDK for timeouts and retries. Add per-replica CRDP scraping and centralized audit collection. Add a shared security service when several teams need one protection contract, policy mapping, or bulk result handling. Use dedicated CRDP deployments only when independent capacity, isolation or policy boundaries justify the operating cost.

Send metrics and audit events to the right places

Use Prometheus or a compatible metrics backend for time series and operational alerts. Send allowlisted CRDP audit records and verified gateway or service events to the SIEM for investigation. Forward selected alert summaries or aggregate signals when they add context; there is rarely a reason to duplicate every scrape in the SIEM.

Capture timestamp, verified caller, operation, bounded outcome, duration, batch item counts, correlation ID and runtime identifiers where available. Keep user identity and observed source IP in restricted audit events only when justified. Exclude bodies, protected values, JWTs, keys, credentials and raw error messages. Log failures that occur before CRDP independently.

Start with four views: caller reliability, CRDP service health, Kubernetes saturation, and security activity. Include API and item failures separately. A failed batch and one failed item describe different problems.

Treat anomalies as leads for investigation

SignalWhat to check
A jump in distinct source IPsCompare with the caller's normal time of day and traffic volume. Check NAT, proxies, deployments and scaling. Count from a trusted edge in the SIEM; do not sum per-replica distinct counts.
A surge in reveals or successful plaintext revealsCompare by caller, operation and policy to historical patterns. Correlate with role changes, planned jobs and large batches. Confirm plaintext outcomes only where the telemetry actually exposes them.
A rise in denials followed by successful revealsLook for new credentials or routes, token expiry, policy changes and unusual bursts. Keep gateway authentication failures separate from CRDP operation failures.
Latency and failures rise togetherCompare client, gateway and backend timing with CPU, restarts, rollout events and CM or identity dependencies before escalating as a security incident.

For scaling, start with measured CPU saturation and replica headroom; add arrival rate or queue depth only if load tests show that the signal improves with added capacity. An IP anomaly, denial spike or completed-work plateau is not a reliable scale trigger.

Use the layers together to narrow an incident

Suppose HRAPP1 and HRAPP2 share a CRDP pool. After a release, HRAPP1 shows a higher item failure rate but gateway responses are still HTTP 200. The application or shared security service can see partial failures inside successful HTTP responses. If HRAPP2 and pod health look normal, start with HRAPP1's input validation, policy mapping or release changes. Check CRDP item counters to see whether the backend observed the same change, but don't assign those shared counters to HRAPP1.

If both callers slow down and CRDP pods become CPU saturated, compare admitted traffic, batch sizes, readiness and the scaling response. If reveal activity rises without a corresponding workload change, check the verified caller, authorization changes and audit results before escalating. These are different investigations even when they start from the same dashboard.

Minimum useful rollout: begin with separate caller credentials, request rates and timing at the gateway, and per-replica CRDP metrics and audit shipping. Add app-side timeout and retry telemetry next. Introduce a shared security service or dedicated CRDP pools only when the extra control or isolation solves a specific problem.

Implement in stages

  1. Identity: register HRAPP1 and HRAPP2 with distinct workload credentials. Map validated client principals or uniquely assigned, enforced gateway subscriptions to canonical app names. Deny unmapped callers. Discard spoofable identity and forwarded-IP headers at the trust boundary.
  2. Request path: use private connectivity to CRDP, TLS, narrow network rules and authorized service-to-service identities. An existing gateway or an approved API security control can protect the boundary. Block direct access that would bypass caller attribution; place the shared service and CRDP in appropriately segmented networks.
  3. Instrumentation: record logical requests at the caller and attempts separately around the dependency call. Record outcomes after inspecting bulk item results. Use bounded metric labels and keep high-cardinality correlation data in logs or traces.
  4. Ownership: application teams own workflow errors and SLOs; platform teams own scrape health and replica capacity; security owns reveal policy, audit access and detection. DBAs review batch impact and audit teams review event completeness and retention.

Build dashboards from counters and latency histograms

Filter to one cluster or preserve the cluster dimension. Apply rate before aggregating counters; substitute corresponding reveal or request counters as needed. Keep missing series and zero traffic visible as no data, and alert separately on scrape health. A ratio of successful items to successful bulk requests is not a reliable average batch size if failed requests can still contribute successful items. Compute true submitted items per request at the request boundary. See Derived PromQL for performance and Prometheus query functions.

Instrument this histogram yourself; it is not a stock CRDP metric. Record one observation per logical service request and name dependency-attempt timing separately. Show p50/p95/p99, request rates, timeouts, retries, item failures and scrape status. Percentiles from different hops are not additive. Use paired timings or traces to isolate network, gateway and backend time.

Define an attribution and event contract

For a new API, put business data under data and operational context under metadata. If an existing API accepts a flat JSON body, preserve that contract and use approved headers for correlation, or introduce the envelope through a versioned endpoint. The envelope below is for your security service; it is not a CRDP request schema.

For example, the wrapper can send POST /v1/security/protect with Content-Type: application/json, approved workload credentials (such as mTLS or Authorization: Bearer <workload-token>), and an optional valid traceparent header. Generate a trusted request ID at ingress and preserve a validated client request ID separately. Client timestamps, workflow and version are optional hints; they do not establish who called, when the event occurred, or whether the action was authorized.

The security service sends only the required fields, resolved policy and approved authorization context to CRDP using the deployed API contract. It records caller_app=HRAPP1 from the verified upstream identity and can record a separate service_name=security-middleware to identify the component that called CRDP. Do not pass the entire business envelope or a self-declared identity through to CRDP. If reveal depends on end-user identity, use a supported, verified delegation model and test that the correct reveal policy applies; a middleware service credential alone does not establish the user's rights.

Reserve an extension object, not a free-text field

Use "extensions": {} for future optional metadata. Register each extension with a namespace, owner, version, schema, size limit and retention rule. For example, a future approved extension could be {"com.example.batch.v1":{"job_type":"scheduled_import"}}. Reject unknown extension keys at the API boundary; reject invalid values and oversized metadata. Never copy arbitrary extensions into logs or metric labels. Add optional fields compatibly; use a new contract version for breaking changes.

Use a short allowlist of metric dimensions: caller_app, environment, operation and a bounded outcome. Use a route template or policy alias only when its cardinality and sensitivity are controlled. Never use request IDs, user IDs, source IPs or arbitrary URLs as metric labels.

For auditing, allowlist event time, validated workload and authorized actor identifiers when available, operation, result, CRDP application and client ID, endpoint, and observed IP where permitted. Validate the actual JSON schema before mapping fields. Verify whether CRDP emits a shared correlation ID; if it does not, do not imply a reliable per-request join. Use gateway-to-service tracing plus time, runtime and operation to narrow CRDP audit investigations. Protect SIEM data with retention limits and role-based access; alert on collector lag, drops and unexpected schema changes.

Collect audit logs on Kubernetes and Docker

CRDP writes JSON audit events separately from performance counters. The documented audit includes who, what, when, application and outcome; the sample includes source_ip. Behind NAT or proxies that address may represent a shared intermediary. Use the following bounded diagnostic collection to inspect recent audit records; set up continuous log shipping for production.

Both streams enter the filter because Docker can emit container logs on stderr. Review a real sample before relying on audit == true or the selected fields; some release schemas place fields inside nested records. A failed CLI call exits nonzero; a successful command that emits no records is not evidence that audit is off. Limit log access and confirm local RBAC or Docker permissions. For Kubernetes restarts, inspect kubectl logs --previous where available; deleted pods and rotated files are not a durable audit store.

In production, use the approved node or container log collector, enrich with namespace/pod/container, parse and allowlist fields before forwarding, and verify buffering, deduplication, restart continuity and delivery monitoring. In AKS, verify collection into Log Analytics with the query below, then route approved events through the organization's SIEM pipeline.

Scale capacity and investigate anomalies separately

For a shared HR pool, set stable workload labels such as app.kubernetes.io/name=crdp and a bounded pool label such as protection_pool=hr. Use them to select targets and dashboards. HRAPP1 and HRAPP2 still share the same pod series. For a dedicated app Deployment and Service, a workload label can represent that app's pool if routing and network policy enforce exclusivity; that costs extra capacity and operational overhead.

Start with the CPU-based autoscaling/v2 example in Autoscaling and operational dashboards. Set resource requests, test load and startup time, and tune replica bounds and stabilization. If CPU misses pressure, consider admitted request rate by pool or backlog via a supported metrics adapter or scaler. One autoscaler should own each Deployment. CRDP success/failure rates and item throughput diagnose capacity; a success rate can flatten under overload. Do not scale on distinct IPs, denials or p99 alone. Keep ready replica and node headroom, and account for rolling surge and entitlement.

Detection starter: in the SIEM, calculate distinct trusted-edge source IPs per verified caller per 15-minute window. Compare with the same time and day over previous weeks. As a pilot, flag a window above 3× its historical median with at least five distinct addresses and 50 requests; tune against real incident and deployment data. Escalate when independent signals agree, such as an unusual reveal burst with new credentials and rising denials. Separate unattributed traffic and suppress planned changes only with an expiry and an audit trail.

Example investigation: if HRAPP1 errors spike but HRAPP2 and CRDP stay healthy, inspect HRAPP1's release and auth configuration first. If both callers slow down while CRDP pods restart and CPU saturates, investigate shared capacity. If reveals rise outside the expected job window without capacity symptoms, correlate verified identities, policy changes and audit outcomes before deciding whether it is abuse.

Validate before using the dashboards for decisions

  1. Send synthetic requests from HRAPP1 and HRAPP2 through the same CRDP pool. Confirm caller views are distinct and the runtime view shows shared work.
  2. Attempt a spoofed caller header, invalid credential, timeout and partially failed batch. Verify attribution, separate transport and item outcomes, and no sensitive values in telemetry.
  3. Restart a pod during a test and verify counter resets, scrape alerts and audit continuity. Test proxy or NAT changes and confirm they do not change caller identity.
  4. Load-test the HPA with realistic bulk sizes and distinct request/item rates. Confirm scale-out, recovery, readiness and rollback under load.
  5. Replay a safe detection scenario. Confirm the alert includes owner, scope, baseline, related events and a link to the runbook.

Examples are starting points. Validate metric and audit schemas, identity mappings, thresholds and collector configuration in a test environment before enabling production alerts or scaling.
