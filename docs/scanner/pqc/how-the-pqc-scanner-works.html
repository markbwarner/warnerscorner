How The PQC Scanner Works

This document explains the PQC side of the migration scanner in plain English. It is meant to help architects, security teams, delivery leads, and developers explain the system quickly without having to read the Python code first.

One-Sentence Explanation

The PQC scanner walks a source tree, classifies each file, looks for direct cryptographic clues in the file content, looks for crypto-related dependencies and SDK references, merges those signals into PQC findings, scores likely migration impact, and then produces reports, CBOM-style component inventory, and HTML summaries.

High-Level Flow

Step 1

Choose Scan Domain

  • --scan pqc
  • --scan pii,pqc
  • pii stays the default if no domain is specified
Step 2

Walk Files And Classify Context

  • Each file is labeled as backend, frontend, docs, test, infrastructure, data access, and related layers
  • This classification affects how findings are interpreted later
Step 3

Run Direct PQC Content Rules

  • Regex-style rules scan file contents for algorithms, TLS, JWT, certificates, SSH, KMS, HSM, and other crypto signals
  • These rules come primarily from config/pqc-rules.json
Step 4

Run Dependency Enrichment

  • The scanner extracts imports, package names, manifests, headers, namespaces, and selected route or wrapper markers
  • It maps those observations to crypto categories using config/dependency-hints.json
Step 5

Merge Findings

  • Direct content findings and dependency-derived findings are combined per file
  • Reference-only files are kept, but downgraded when appropriate
Step 6

Score Migration Impact

  • The scanner estimates complexity and recommended remediation lane
  • Examples: dependency-driven, protocol stack, PKI lifecycle, application signing, custom refactor
Step 7

Write Reports

  • JSON, CSV, HTML, and CBOM-style outputs are produced
  • HTML adds vendor rollups, glossary guidance, and PQC-capable status tags

What The Scanner Is Actually Looking For

Direct file-content signals

Examples: RSA, ECDSA, KeyStore, X509Certificate, JWT, ML-KEM, HQC, FrodoKEM.

Dependency signals

Examples: Maven coordinates, NuGet packages, npm modules, Go modules, Python imports, Java imports, C headers, .NET namespaces.

Wrapper and route signals

Examples: custom CRDP endpoints, internal helper class names, and crypto-facing route markers that indicate managed crypto flows.

File context signals

The same algorithm mention means something different in a backend service, a front-end UI panel, a test harness, or a readme.

What Comes Out

Per-file findings

Each file gets its own PQC finding list, category totals, migration classes, complexity, notes, and recommended action.

Dependency and CBOM rollups

Observed packages and SDK markers are rolled up into vendor families, ecosystems, and CBOM component inventory.

Human-readable HTML interpretation

The HTML report explains the counts, adds vendor grouping, and applies PQC-current, PQC-specialized, or PQC-watch-list tags where appropriate.

config/cbom-vendor-families.json Vendor/source-family rollup rules Groups observed components and dependency references into families like Thales, AWS, Azure, Oracle, OpenSSL, or custom wrappers.

What Is Config-Driven Vs Code-Driven

Mostly config-driven

  • Which algorithm strings are recognized as direct PQC content matches
  • Which dependency names count as crypto-related
  • How vendor/source family grouping works
  • Plain-English wording for dependency explanations

Mostly code-driven

  • How files are walked and classified
  • How imports and manifests are parsed by language
  • How multiple signal types are merged into one file report
  • How complexity and recommended actions are scored
  • How frontend, docs, and test content is downgraded or interpreted

PQC Status Tags In The HTML Report

PQC-current
Current or selected NIST-aligned signals such as ML-KEM, ML-DSA, SLH-DSA, FN-DSA, or HQC.
PQC-specialized
Specialized approved PQC signals such as XMSS, XMSSMT, LMS, or HSS.
PQC-alias
Alias or legacy naming such as Kyber, Dilithium, Falcon, or SPHINCS+.
PQC-watch-list
Experimental or watch-list naming such as FrodoKEM, Classic McEliece, BIKE, NTRU, or SABER.
Front-end files are treated carefully. A browser file only receives a PQC status tag when it contains both explicit PQC algorithm signals and real browser-side crypto implementation markers such as window.crypto or crypto.subtle. That keeps ordinary UI text or status panels from being mislabeled as implementation owners.

How PQC Complexity Is Determined

The PQC scanner assigns each file a separate migration-complexity rating of low, medium, or high. This is not a vulnerability severity score. It is a directional estimate of how much migration design, integration, coordination, and testing effort the file is likely to trigger.

Thresholds

  • low: score less than 6
  • medium: score from 6 up to but not including 12
  • high: score 12 or greater

What pushes complexity up

  • Implementation-style findings instead of reference-only mentions
  • Custom refactor, signing, key-exchange, PKI, protocol, and dependency-driven migration classes
  • More distinct crypto algorithms and more likely implementation ownership

What pulls complexity down

  • Test, documentation, and other reference-oriented files
  • Front-end-only files with no clear implementation ownership
  • Files that mostly mention crypto rather than implementing or configuring it

The current scoring heuristic is:

score =
  (implementation findings x 3.0)
  + (distinct algorithm names x 2.0)
  + (CUSTOM_REFACTOR findings x 4.0)
  + (APPLICATION_SIGNING findings x 3.0)
  + (APPLICATION_KEY_EXCHANGE findings x 3.0)
  + (PKI_CERTIFICATE_LIFECYCLE findings x 2.0)
  + (PROTOCOL_STACK findings x 2.0)
  + (DEPENDENCY_DRIVEN findings x 1.5)
  + context and PQC-signal adjustments

In plain English, a file trends toward high when it appears to own real crypto integration behavior such as signing, certificates, key exchange, vendor SDK integration, TLS, SSH, KMS, or HSM coordination. A file trends toward low when it looks more like documentation, testing, a UI reference, or a secondary mention.

Example: How One File Becomes A PQC Finding

Example file: a Java service that uses ML-KEM, LunaProvider, KeyStore, and JWT signing.
Signal A

Content Match

ML-KEM matches the direct PQC algorithm rule.

Signal B

Dependency Match

LunaProvider and related imports are recognized as crypto-relevant dependency signals.

Signal C

Category Mapping

The file may accumulate PQC_CAPABLE_ALGORITHM, KMS_OR_HSM_ASYMMETRIC, and CERTIFICATE_USAGE.

Signal D

Posture Scoring

The scanner decides whether this looks low, medium, or high complexity and what remediation lane fits best.

Signal E

Report Output

The HTML report may show a green PQC-current tag plus dependency notes and likely change-target guidance.

Simple Explanation You Can Reuse With Others

The PQC scanner works in two main passes. First, it looks directly inside files for cryptographic clues such as algorithm names, certificate handling, TLS settings, signing code, or KMS or HSM usage. Second, it enriches that result by looking at imports, packages, manifests, headers, and wrapper markers so it can tell whether the code is using vendor SDKs, PKI tooling, or protocol-stack components. It then merges those signals, scores likely migration effort, and writes reports that help teams focus on the files most likely to require real change.
