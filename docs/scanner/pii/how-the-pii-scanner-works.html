How The PII Scanner Works

This document explains the PII side of the migration scanner in plain English. It is meant to help architects, delivery teams, DBAs, and developers explain how the scanner finds sensitive-data impact and how it decides which files are more likely to require real migration work.

One-Sentence Explanation

The PII scanner walks a source tree, classifies each file, looks for likely sensitive-data references in identifiers and literals, estimates whether the work is more likely code-change or JDBC or data-access oriented, correlates likely ownership across UI, service, and persistence layers, and then produces reports that help teams focus on the files most likely to matter.

High-Level Flow

Step 1

Choose Scan Domain

  • --scan pii
  • --scan pii,pqc
  • pii is the default if no domain is specified
Step 2

Walk Files And Classify Context

  • Each file is labeled as frontend, backend, data access, docs, test, infrastructure, and related layers
  • This affects later ownership and migration interpretation
Step 3

Detect PII Clues

  • Identifier-style keyword matching
  • Custom customer rules
  • Custom regex literal detection when needed
Step 4

Extract Architecture Hints

  • REST endpoints, payload fields, SQL verbs, table names, system-of-record paths, and JDBC markers are extracted
  • This turns raw field hits into migration signals
Step 5

Estimate Migration Path

  • The scanner estimates whether the work looks code-change-heavy, JDBC-substitution-friendly, or mostly reference-only
  • It also assigns low, medium, or high complexity
Step 6

Assess Ownership

  • Frontend collectors, backend API owners, supporting DTOs, and data-access owners are separated
  • Related files are correlated into likely change chains
Step 7

Write Planning Outputs

  • JSON, CSV, file-report JSON or CSV, and DBA planning SQL are produced
  • Optional workbook tools build PII-assessment-informed planning artifacts

What The Scanner Is Actually Looking For

Identifier and field names

Examples: ssn, email, phoneNumber, acctNbr, householdNbr, customerDob.

Customer-defined aliases

Custom rules let teams search for organization-specific names that are meaningful locally even if they are not standard PII terminology.

Integration and persistence clues

Examples: SQL verbs, JDBC markers, endpoint mappings, REST calls, payload fields, repository hints, and data-access patterns.

Role in the flow

The same PII field reference means something different in a display-only React screen, a Spring controller, a DTO, or a JDBC repository.

What Comes Out

Per-file match and category totals

Each file gets line-level PII matches, category summaries, complexity, and migration notes.

Likely change-target guidance

The scanner separates support models and UI references from likely API-side or data-access-side change owners.

Delivery-ready planning outputs

CSV exports, DBA planning SQL, and workbook-oriented outputs help teams turn scanner results into scoping and execution work.

How Data Elements Are Detected

1. Built-in identifier matching

The scanner tokenizes code-like identifiers, normalizes naming style, and compares the normalized form to built-in PII keyword rules.

Examples:

  • accountNumber becomes account_number
  • acctNbr becomes a normalized alias that can still match customer-defined keywords
  • customerDob can match a date-of-birth style rule after normalization

2. Custom keyword patterns

Customers can define their own business-specific field names and categories without changing Python code. This is useful when the data is sensitive to the organization but does not use standard PII terminology.

3. Custom regex patterns

Customers can also define literal formats, such as account-number strings, household IDs, or compensation values, when identifier matching alone is not enough.

4. Literal-format matching

Literal formats such as account numbers, household IDs, or salary-like values can be detected through customer-defined regex patterns when identifier matching alone is not enough.

In simple terms, the scanner does not only look for exact field names. It first normalizes identifiers, then checks them against built-in and customer-defined aliases, and can optionally look for literal formats too. That is why names like acct_nbr, accountNum, and customer_account_number can all be treated as the same business concept when configured.
Detection type Best for Example
Built-in keyword rules Common PII field names email, phone, ssn
Custom keyword rules Customer vocabulary and aliases acct_nbr, hh_id, annual_salary
Custom regex rules Literal value formats HH-123456, 123456789012, $125,000
Literal-format matching Literal text and string analysis Free-form sensitive text in comments or strings

How Custom Elements Are Supported

Customer-specific PII definitions are supplied through JSON files rather than hard-coded edits to the scanner. There are two main extension styles.

Custom keyword example

Use this when you want identifier-like names to map to a customer-defined category.

{
  "custom_patterns": [
    {
      "name": "account-number",
      "category": "CUSTOM_ACCOUNT_NUMBER",
      "keywords": [
        "account_number",
        "account_num",
        "account_nbr",
        "acct_number",
        "acct_num",
        "acct_nbr",
        "accnt_nbr",
        "customer_account_number"
      ],
      "impact_hint": "Customer-defined account number field"
    },
    {
      "name": "household-id",
      "category": "CUSTOM_HOUSEHOLD_ID",
      "keywords": [
        "household_id",
        "household_identifier",
        "family_household_id",
        "household_nbr",
        "household_num",
        "hh_id",
        "hh_number"
      ],
      "impact_hint": "Customer-defined household identifier"
    },
    {
      "name": "salary",
      "category": "CUSTOM_SALARY",
      "keywords": ["salary", "annual_salary", "base_salary", "compensation_amount"],
      "impact_hint": "Customer-defined compensation field"
    }
  ]
}

Custom regex example

Use this when the signal is a literal format rather than just a field name.

{
  "custom_regex_patterns": [
    {
      "name": "household-id-literal",
      "category": "CUSTOM_HOUSEHOLD_ID_LITERAL",
      "pattern": "HH-[0-9]{5,10}",
      "impact_hint": "Literal household identifier format"
    },
    {
      "name": "account-number-literal",
      "category": "CUSTOM_ACCOUNT_NUMBER_LITERAL",
      "pattern": "\b[0-9]{10,12}\b",
      "impact_hint": "Literal account number format"
    },
    {
      "name": "salary-literal",
      "category": "CUSTOM_SALARY_LITERAL",
      "pattern": "\$[0-9]{2,3},[0-9]{3}",
      "impact_hint": "Literal salary amount format"
    }
  ]
}
A useful way to explain this to others: custom keyword rules help the scanner understand what your organization calls the data, while custom regex rules help it understand what the data values look like.

How To Run With Custom PII Definitions

The usual pattern is to keep custom keyword and regex definitions in a JSON file and pass it at runtime with --custom-patterns.

python E:\codex\work\migrationpp.py E:/codex/work/migration/sample_code --scan pii --custom-patterns E:/codex/work/migration/config/pii/examples/custom-patterns.example.json

If you want customer-defined keyword categories to replace the built-in keyword category for the same identifier, add --custom-patterns-override-defaults.

python E:\codex\work\migrationpp.py E:/codex/work/migration/sample_code --scan pii --custom-patterns E:/codex/work/migration/config/pii/examples/custom-patterns.example.json --custom-patterns-override-defaults

What Is Config-Driven Vs Code-Driven

Mostly config-driven

  • Customer-specific keyword categories and aliases
  • Customer-specific regex patterns
  • Whether custom rules override built-in keyword categories

Mostly code-driven

  • How identifiers are normalized and matched
  • How endpoints, payload fields, SQL verbs, and JDBC markers are extracted
  • How ownership confidence is estimated
  • How frontend reference-only files are separated from likely back-end or data-access owners
  • How complexity and recommended actions are scored

Typical Output Meanings

review_code_change
The file looks like a likely implementation-side change target where application logic probably needs direct review.
review_jdbc_substitution
The scanner sees stronger JDBC or direct data-access clues, which may support lower-code-impact protection or substitution planning.
frontend_reference_only
The file touches PII, but it looks more like a UI or proxy reference than the primary implementation owner.
supporting_model_only
The file looks like a DTO, request or response model, payload type, or other supporting structure rather than the main change owner.
The PII scanner is not just counting fields. It is trying to answer a more practical question: where is the work likely to land if we need to protect or migrate this sensitive data flow?

Example: How One File Becomes A PII Change Target

Example file: a Spring Boot repository or service that handles ssn, emailAddress, and householdNbr, calls a database, and issues SQL updates.
Signal A

PII Match

Identifiers like ssn and emailAddress match built-in or customer-defined PII patterns.

Signal B

Architecture Clues

The scanner sees SQL verbs, JDBC markers, or repository-style access that suggests persistence ownership.

Signal C

Ownership Logic

The file is more likely labeled jdbc_candidate or data_access_owner than a supporting model or frontend reference.

Signal D

Path Estimation

The scanner estimates whether the work is better framed as code change or JDBC-style substitution planning.

Signal E

Report Output

The file may appear in likely-change-targets.csv with review_jdbc_substitution, jdbc_tables, and related planning columns.

Simple Explanation You Can Reuse With Others

The PII scanner works in two practical layers. First, it finds likely sensitive-data references in identifiers, fields, payloads, and optional literal text. Second, it asks where those references appear in the application architecture: a frontend display, a backend API, a supporting model, or a JDBC and data-access layer. That allows it to move beyond raw field counting and give teams a better first-pass answer about where migration, protection, and testing work are most likely to concentrate.
